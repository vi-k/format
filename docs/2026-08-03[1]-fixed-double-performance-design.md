# Производительность фиксированного форматирования `double`

## Контекст

Format 3 форматирует `double` в режиме `f` на 22–26% медленнее Format 2 в
JIT и на 35–39% медленнее в AOT. Остальные исследованные ветви `double` не
показывают общей регрессии: `g`, `nan` и `inf` быстрее прежней реализации.

Причина локализована в точном округлении двоичного значения через `Binary64`
и `BigInt`. Оно необходимо для Python-совместимого round-half-even, но примерно
в 5,7 раза дороже `double.toStringAsFixed()`. Безусловная замена невозможна:
встроенный метод округляет `2.5` до `3` и `1.25` до `1.3`, тогда как контракт
Format 3 требует `2` и `1.2`.

## Цель

Ускорить конечный формат `f`, сохранив побитово точное Python-совместимое
округление, поддержку точности до 100000 знаков и одинаковое поведение JIT,
AOT и JavaScript. Оба повторных JIT- и AOT-прогона ключевых сценариев должны
иметь отношение Format 3 / Format 2 не выше 1,05.

## Решение

`_formatFixed` получает исходный `double`. `Binary64` создаётся лениво только
при переходе на точный путь, а перед ним вызывается приватный fast path со
следующими ограничениями:

1. точность находится в диапазоне `0…20`, поддерживаемом
   `toStringAsFixed()`;
2. модуль значения меньше `1e21`, чтобы встроенный метод не переключился на
   экспоненциальную запись;
3. `abs(value) * 10^precision` меньше `2^52`, поэтому целая часть и половина
   представимы без потери двоичной точности;
4. если дробная часть масштабированного значения равна `0.5`, а целая часть
   чётная, fast path запрещён: именно здесь half-away и half-even расходятся.

Первые 21 степени десяти хранятся в неизменяемой таблице `double`. Для
доказуемо безопасного значения тело создаётся через
`abs(value).toStringAsFixed(precision)`. При нулевой точности alternate form
добавляет точку. Признак округления к нулю определяется по масштабированному
модулю, а знак по-прежнему обрабатывается общим layout-кодом.

Любое значение вне этих условий без изменений проходит через существующие
`Binary64.roundDecimal`, `_fixedFromRounded` и round-half-even. Fast path
используется как общей brace-ветвью, так и printf-ветвью, потому что обе
вызывают `_formatFixed`.

Для распространённых спецификаций `.0f`…`.20f` и `.0F`…`.20F` добавлен узкий
ASCII-путь разбора с кэшированными `_FormatSpec`. Все остальные спецификации,
включая точность выше 20, по-прежнему проходят через полный Unicode-парсер.

## Проверки крайних значений

Тесты должны явно закрепить:

- отсутствие двойного минуса у `sprintf('%d', minInt)`;
- `minInt`, `maxInt`, ноль и `BigInt` непосредственно за границами VM `int`;
- `2.5`, `3.5`, `1.25` и `1.75` для обеих сторон half-even;
- `0.0`, `-0.0`, минимальное субнормальное и максимальное конечное `double`;
- точность 20, точность 21 и большое фиксированное значение;
- неизменность alternate form, знака и нормализации отрицательного нуля.

Ожидания задаются литералами и проверяют публичные `format`/`sprintf`, а не
приватный предикат.

## Измерения

В release harness добавляется отдельный ключевой сценарий большого `double`
с шаблоном `{:.2f}` и значением `12345678901234.568`. Производительность
проверяется двумя gateable JIT- и двумя gateable AOT-отчётами на одном чистом
коммите. Нативные отчёты используют по 1000 операций на раунд, чтобы выбросы
JIT не определяли медиану. Smoke-отчёты не используются для решения о
регрессии.

Исходный `example/bin/benchmark.dart` запускается как пользовательская
проверка. Ошибка двойного минуса принадлежит замороженному sprintf7 baseline;
его исходники не изменяются, а корректное поведение Format 3 закрепляется
отдельным тестом.

## Вне области работ

- замена всего алгоритма decimal conversion;
- изменение Python-совместимого округления;
- исправление или переписывание замороженных Format 2 и sprintf7 baseline;
- оптимизация `e`, `g`, `%`, `nan`, `inf` и общего Unicode-парсера.
