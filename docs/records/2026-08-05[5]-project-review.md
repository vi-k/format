# Executive summary

`format` 3.0.0 — зрелая, необычно тщательно сделанная библиотека. Численное ядро и слой парсинга
находятся на уровне, которого большинство реализаций форматирования не достигает: ноль расхождений
с CPython на ~1.95 млн кейсов и ноль расхождений с C `printf` вне `%a` на ~1.48 млн кейсов.
Двухпутёвая архитектура (Template IR + legacy-оракул) — главный архитектурный риск проекта — закрыта
не обещаниями, а конструкцией: классификатор IR *зондирует* настоящие валидаторы вместо копирования
их правил, всё непокрытое безопасно падает в legacy, а паритет проверяется дифференциальным
фаззингом. Два независимых прохода по ~640 000 пар не нашли ни одного расхождения.

Главные риски лежат **не в семантике форматирования, а вокруг неё**:

1. **Пакет нельзя публиковать в текущем виде без потери баллов.** Опубликованный архив содержит
   `test/`, три файла которого импортируют исключённый `.pubignore` каталог `benchmark/`. На
   реконструированном архиве `dart analyze` даёт **159 ошибок**. `pana` анализирует пакет целиком.
2. **Контракт «всё падает типизированным `FormattingException`» нарушается в конструкторе `Format`** —
   исключение из пользовательского геттера `specifier` уходит наружу как `StateError`.
3. **Гейты производительности не могут поймать регрессию.** Пороги выставлены против медленных
   конкурентов с запасом ×5–×10; библиотеку можно замедлить втрое-впятеро, и гейт вернёт `passed`.
   Вдобавок гейты вообще не запускаются в CI.
4. **Ресурсные асимметрии**: квадратичный разбор числового индекса (DoS на внешнем шаблоне),
   обрыв производительности ×7 на 513-м шаблоне, кэш ограничен числом записей, но не байтами.

Общий уровень качества: **высокий**. Ни одна находка не даёт неверного результата форматирования.
Всё найденное — либо инфраструктура публикации, либо граничные ресурсные сценарии, либо
несоответствия документации. Оценка готовности к 3.0.0: **закрыть H1 и H2 обязательно**, остальное
можно распределить по 3.0.x.

# Project overview

`format` — Dart-библиотека строкового форматирования, реализующая **два независимых
мини-языка** под одной иммутабельной конфигурацией:

- Python-подобные фигурные скобки (`{}`, `{0}`, `{name}`, `{v.attr[key]!r:{w}.2f}`);
- printf (`%s`, `%#08x`, `%*.*f`, `%a`).

**Публичный вход** (`lib/format.dart`) — четыре функции (`format`, `formatWith`, `sprintf`,
`vsprintf`), их инстансные двойники на классе `Format`, три интерфейса расширения
(`Formatter`, `AttributeLookup`, `Representation`), `NumberLocale`, `TextUnit`, два enum'а профиля
double и sealed-иерархия исключений.

**Потоки данных.** Шаблон → `_cachedBraceTemplate` / `_cachedPrintfTemplate`
(`lib/src/template_cache.dart`) → парсер (`brace_parser.dart` / `printf_parser.dart`) → AST
(`brace_ast.dart` / `printf_ast.dart`) → **классификатор и компилятор в IR**
(`template_ir.dart`, ~1600 строк) → программа из op-ов, исполняемая поверх `CharSink`
(`char_sink.dart`, буфер `Uint16List` с оптимизацией `_single`). Всё, что классификатор не
распознал как «горячее» (группировка разрядов, `n`, `c`, `a`, кастомные форматтеры,
многоюнитный fill, небезопасные ширины), компилируется в `_BraceFallbackOp`/`_PrintfFallbackOp`,
который дословно исполняет **legacy-путь** (`brace_processor.dart`, `printf_processor.dart`,
`value_formatter.dart`, `printf_formatter.dart`, `number_format.dart`).

**Численное ядро** — `binary64.dart` (точная десятичная развёртка double через `BigInt`,
half-even округление на точных рациональных), `number_format.dart` (Python-совместимый профиль),
`dart_double_format.dart` (профиль Dart SDK). Профиль выбирается через `DoubleFormatMode`.

**Границы модулей** соблюдены: `lib/format.dart` экспортирует минимум; всё остальное —
`part of 'engine.dart'`, единая приватная библиотека. Подпакет `packages/format_intl` изолирует
зависимость от `intl`. Бенчмарки, фикстуры и генераторы (`benchmark/`, `tool/`) вне публикуемого
кода.

# Critical and high-severity findings

## H1. Опубликованный архив не проходит статический анализ — 159 ошибок

- **severity:** High · **confidence:** high (проверено лично)
- **Где:** `test/benchmark_gates_test.dart:6-8`, `test/benchmark_scenarios_test.dart:6-8`,
  `test/benchmark_isolation_test.dart:5`; `.pubignore:4`
- **Проблема.** Три тестовых файла импортируют `../benchmark/gates.dart`, `../benchmark/model.dart`,
  `../benchmark/scenarios.dart`, `../benchmark/runner.dart`,
  `../benchmark/baselines/format20/format20.dart`. `.pubignore` исключает `/benchmark/`, но `test/`
  в архив входит целиком.
- **Сценарий.** Реконструировал содержимое архива (rsync с фильтрами `.pubignore`), выполнил
  `dart pub get && dart analyze`:

  ```
  159 errors: 92 в test/benchmark_scenarios_test.dart,
              61 в test/benchmark_gates_test.dart,
               6 в test/benchmark_isolation_test.dart
  ```
- **Последствия.** `pana` анализирует пакет целиком — прямая потеря баллов в разделе
  «Pass static analysis» на витрине pub.dev. Любой, кто распакует пакет и запустит `dart test`,
  получит три невалидных файла. Локальный `dart analyze` этого не видит, потому что `benchmark/`
  на месте — дефект существует только в артефакте публикации.
- **Исправление.** Перенести эти три файла в `benchmark/test/` и подключить отдельным шагом CI,
  либо добавить `/test/benchmark_*.dart` в `.pubignore`, либо не публиковать `test/`.
  Плюс CI-шаг «архив самодостаточен»: собрать архив, `pub get`, `analyze`, `test`.

## H2. Конструктор `Format` пропускает не-`FormattingException` наружу

- **severity:** High · **confidence:** high (проверено лично)
- **Где:** `lib/src/format.dart:150` (`final name = formatter.specifier;`),
  `lib/src/format.dart:53-55`; контракт объявлен в доккомментарии `lib/src/format.dart:39-40`
- **Проблема.** `_validateConfiguration()` читает пользовательский геттер `specifier` без guard'а.
  Весь остальной пакет последовательно оборачивает пользовательский код в
  `FormatExtensionException` (шесть мест: `value_formatter.dart:81-98,126-155,157-170`,
  `field_resolver.dart:96-133`, `representation.dart:169-197`, `number_format.dart:733-741`) —
  конструктор из этой дисциплины выпал.
- **Сценарий.**

  ```dart
  final class ThrowingSpecifier extends Formatter<Object> {
    @override String get specifier => throw StateError('specifier boom');
    ...
  }
  Format(formatters: [ThrowingSpecifier()]);
  // -> StateError: Bad state: specifier boom   (НЕ FormattingException)
  ```
  Реалистичный триггер — `late final String specifier`, не инициализированный к моменту
  конструирования: `LateInitializationError`.
- **Последствия.** Нарушен главный контракт пакета и явное обещание доккомментария
  («throws `FormatConfigurationException` when the configuration is invalid»). Код, обернувший
  конфигурацию в `on FormattingException`, падает необработанным исключением.
- **Исправление.** Читать `specifier` через тот же guard-паттерн и оборачивать в
  `FormatConfigurationException`. Тот же незащищённый доступ — в `value_formatter.dart:52`
  (построение `AmbiguousFormatterException`) и `value_formatter.dart:92` (внутри `catch`).

## H3. Квадратичный разбор числового индекса поля — усилитель DoS ×700

- **severity:** High (при внешних шаблонах), Medium (при только литеральных) · **confidence:** high
  (проверено лично)
- **Где:** `lib/src/brace_parser.dart:307-318` (`_decimalIndex`), вызовы — `:190-201`, `:270-275`
- **Проблема.** Для любого числового индекса выполняется `digits.join()` + `BigInt.parse(...)` и
  только потом сравнение с 2^63−1. `BigInt.parse` в Dart — O(n²). Уже при 20 цифрах число заведомо
  вне int64, но BigInt строится целиком.
- **Сценарий (мои замеры).**

  | вход | время |
  |---|---|
  | `'{' + '9'*100000 + '}'` | 52 мс |
  | `'{' + '9'*300000 + '}'` | 309 мс |
  | `'{' + '9'*600000 + '}'` | **1184 мс** |
  | `'%' + '9'*600000 + 'd'` (printf, `int.tryParse`) | **5 мс** |

  Отказ не кэшируется (`template_cache.dart:11-18` кладёт в кэш только успешный разбор), поэтому
  цена платится на каждом вызове: 10 повторов шаблона со 100 000 цифр — 381 мс.
- **Последствия.** Пакет сам объявил недоверенный шаблон частью модели угроз — есть потолок
  `_maximumSafeFormatOption = 100000` (`printf_processor.dart:7`) и проверка ширины
  (`format_spec.dart:91-98`). Индексная ветка из этой политики выпала.
- **Исправление.** Отбросить ведущие нули и отказать, если значащих цифр > 19, до построения
  BigInt; либо перейти на `int.tryParse` с явной проверкой длины (это заодно закрывает M4).

## H4. Один набор порогов обслуживает три рантайма, в которых запас различается на порядок

> Уточнено 2026-08-07 после замеров всех трёх рантаймов. Первоначальная формулировка
> («гейты физически не могут поймать регрессию») опиралась на JIT-данные и для JS неверна:
> там пороги, наоборот, почти связывающие. Ниже — исправленная версия.

- **severity:** High · **confidence:** high (проверено лично: по два прогона jit, aot и js)
- **Где:** `benchmark/gates.dart:8-12`
- **Проблема.** Пять глобальных констант (`_braceHotMeanLimit = 1.02`,
  `_printfHotMeanLimit = 0.80`, `_printfColdMeanLimit = 0.90`, key-лимиты 1.05 и 1.02)
  применяются ко всем рантаймам сразу. Фактический запас:

  | рантайм | диалект/фаза | geometric mean (2 прогона) | порог | запас |
  |---|---|---|---|---|
  | jit | braces hot | 0.1165 / 0.1204 | 1.02 | ×8.5 |
  | jit | printf hot | 0.0964 / 0.0957 | 0.80 | ×8.3 |
  | jit | printf cold | 0.1348 / 0.1320 | 0.90 | ×6.7 |
  | aot | braces hot | 0.0954 / 0.0951 | 1.02 | ×10.7 |
  | aot | printf hot | 0.0933 / 0.0931 | 0.80 | ×8.6 |
  | **js** | **printf hot** | **0.3862 / 0.4005** | 0.80 | **×2.0** |
  | **js** | **printf cold** | **0.9116 / 0.8333** | 0.90 | **×1.0 — run1 уже за порогом** |

  Худшие key-сценарии: jit 0.343, aot 0.394, **js 1.125** при пороге 1.02.
- **Последствия.** На JIT и AOT библиотеку можно замедлить в 8–10 раз, и гейт вернёт
  `passed: true`. На JS запаса нет вовсе: `printf cold` в первом прогоне (0.9116) уже нарушает
  порог, а key-сценарий `printf.dynamic.cold` даёт 1.125 — гейт проходит только благодаря
  правилу «нарушение должно повториться в обоих прогонах» (`gates.dart:59-62`). То есть
  тот же самый набор констант одновременно бесполезен на двух рантаймах и балансирует
  на грани ложного срабатывания на третьем.
- **Исправление.** Пороги должны быть **по рантаймам**, а не глобальными: для jit/aot
  примерно 0.25–0.35 (2.5× от наблюдаемого), для js — исходя из фактического паритета,
  а не от чисел VM. Простое ужесточение глобальных констант сломает JS-гейт немедленно.
  Учесть шум: при 1000 операций разброс между прогонами достигает 20–190 %, так что порог
  тоньше ~15 % физически неразличим.
- **Замечание.** В `benchmark/results/` нет ни одного зафиксированного gate-отчёта, то есть
  библиотека ни разу не сравнивалась сама с собой; `HANDOFF.md:266-270` при этом ссылается на
  гейт как на «более строгий релизный харнес».

## H4b. На JS измерения квантованы разрешением таймера в 1 мс

- **severity:** High · **confidence:** high (проверено лично на шести отчётах)
- **Где:** `benchmark/runner.dart:9-10` (`_nativeOperations = 1000`,
  `_javascriptOperations = 10000`)
- **Проблема.** Под dart2js `Stopwatch` имеет разрешение 1 мс, а раунд из 10 000 операций
  укладывается в единицы миллисекунд. В отчёте это видно прямо:

  ```
  js : 21 различных медиан, все — точные кратные 1 000 000 нс
  jit: 45 различных медиан, произвольные (75042, 84459, 85833, …)
  ```
  Значит каждое JS-отношение — дробь маленьких целых: `2000000/5000000 = 0.400`,
  `1000000/2000000 = 0.500`. Ошибка квантования на самых быстрых сценариях достигает ±50 %.
- **Следствие — воспроизводимость.** Разброс между двумя независимыми прогонами:

  | уровень | jit | aot | js |
  |---|---|---|---|
  | geometric mean фазы | 2.1–4.8 % | 0.2–2.9 % | 2.3–7.1 % |
  | худший отдельный сценарий | 36.7 % | 26.4 % | **150 %** |

  На JS девять сценариев из 45 расходятся между прогонами больше чем на 25 %.
- **Последствия.** Агрегаты (geometric mean по фазе) воспроизводимы и пригодны для гейта.
  Отдельные сценарии на JS — нет: допуск 1.25/1.40 лежит **ниже** уровня шума, поэтому
  per-scenario гейт там даст либо ложные срабатывания, либо пропуски. Записывать эталон до
  исправления нельзя — он зафиксирует случайные числа.
- **Исправление.** Калибровать число операций по сценарию, а не задавать константой.
- **Статус: исправлено 2026-08-07.** Раунд калибруется по каждому сценарию и каждому движку
  до цели `max(10 мс, 100 тактов часов)`, где разрешение часов измеряется, а не берётся из
  `Stopwatch.frequency`. Результат:

  | | до | после |
  |---|---|---|
  | худший разброс сценария, jit | 36.7 % | 5.2 % |
  | худший разброс сценария, js | 150 % | 8.7 % |
  | сценариев с разбросом > 10 % | 9 | 0 |
  | время JIT-прогона | 40 с | 21 с |
  | время JS-прогона | ~30 с | 198 с |

  Отношение считается по времени на операцию, поэтому движки могут иметь разные счётчики.
  Побочный эффект — см. M9 ниже: длинные раунды усилили доминирование горячего пути в
  «холодной» фазе.

## H4a. На JS Format медленнее конкурента, и заметно

> Переизмерено 2026-08-07 на CI-железе (AMD EPYC, linux_x64, Node v24.8.0) после
> калибровки замеров и починки холодной фазы. Числа ниже в исходной редакции опирались
> на квантованные и артефактные данные; итоговая картина оказалась **хуже** первой оценки.

**severity: High · confidence: high.** Записанный эталон (`benchmark/results/gate-baseline.json`):

| фаза | jit | aot | **js** |
|---|---|---|---|
| braces cold | 1.025 | 1.031 | **5.903** |
| braces hot | 0.105 | 0.096 | **1.039** |
| printf cold | 0.251 | 0.314 | **1.342** |
| printf hot | 0.102 | 0.097 | 0.373 |

Худшие сценарии на JS (ratio > 1 — медленнее замороженной базы):

```
brace.literal.cold           9.28 / 9.13     (на VM: 0.98)
brace.int.large_decimal.hot  8.88 / 8.83
brace.parser_heavy.cold      5.22 / 5.69     (на VM: 1.10)
brace.double.general.hot     4.13 / 4.28
brace.fields.10.cold         4.02 / 4.18     (на VM: 1.00)
printf.literal.cold          2.70 / 2.46     (на VM: 0.39)
```

Сопоставление с VM показывает, что это именно web-специфика, а не общая медленность:
на тех же холодных сценариях VM даёт паритет (0.98–1.10), а JS — от 4 до 9.3.

~~`brace.int.large_decimal` (8.9×) объясняется прямо: это `{:d}` со значением 2^53−1, где
`_exceedsWebSafeInt` отправляет каждый вызов через `BigInt`.~~

**Это утверждение неверно, снято 2026-08-08.** Проверка показала два изъяна. Во-первых,
`_exceedsWebSafeInt` использует строгое сравнение, поэтому ровно 2^53−1 границу **не**
превышает и в ветку `BigInt` не попадает вовсе. Во-вторых, реальной причиной был
`CharSink`/`Uint16List` round-trip: после его исправления сценарий даёт **0.70** вместо 8.88,
без единой правки в целочисленном пути.

Настоящая стоимость `BigInt` нашлась в другом месте — у значений, которые действительно
превышают 2^53−1, и матрица бенчмарка их не покрывает: `{:d}` от 2^53 стоил **939 нс**
против 174 нс на безопасном пути. Исправлено там же: ниже 1e21 точные цифры даёт

## H6. Обрыв производительности ×7 на 513-м шаблоне (FIFO-вытеснение)

- **severity:** High · **confidence:** high (проверено лично, обе стороны — по возрастанию и по
  убыванию N)
- **Где:** `lib/src/template_cache.dart:3,12-18,25-28`
- **Проблема.** Ёмкость 512, вытеснение — чистый FIFO (`keys.first`), учёта попаданий нет. Для
  циклического рабочего набора N > capacity это классический thrash с 0 % попаданий.
- **Сценарий (мои замеры, 40 000 итераций на точку).**

  ```
  asc  n=512 -> 105.0 ns/op     desc n=512 -> 96.2 ns/op
  asc  n=513 -> 1088.3 ns/op    desc n=513 -> 691.7 ns/op
  asc  n=600 -> 706.2 ns/op     desc n=600 -> 701.8 ns/op
  asc  n=1024-> 704.3 ns/op     desc n=1024-> 700.2 ns/op
  ```
  При N ≥ 513 стоимость равна полностью холодному пути — кэш не даёт ничего.
- **Последствия.** Приложение с 513 разными шаблонами (реалистично для сервиса с i18n-строками или
  логгера с богатым набором сообщений) работает в 7 раз медленнее, чем с 512, и это невозможно
  диагностировать: ни размера кэша, ни статистики попаданий, ни настройки ёмкости в публичном API
  нет (`debugTemplateCacheCapacity`, `debugClearTemplateCaches` намеренно не экспортированы,
  `template_cache.dart:31-32`).
- **Исправление.** LRU от циклического паттерна не спасает — нужен random/CLOCK-eviction (сохраняет
  ~(1−N/cap) попаданий вместо нуля) либо сегментированный кэш; как минимум — публичная настройка
  ёмкости. Плюс `keys.first` создаёт `Iterable` + итератор на каждое вытеснение.

- **Статус: закрыто 2026-08-08.** Политика вытеснения заменена на случайную (обрыв
  6.45× → 1.7×), а ёмкость, размер и очистка вынесены в публичный API:
  `templateCacheCapacity`, `templateCacheSize`, `clearTemplateCache()`. Нулевая ёмкость
  отключает кэш — для нагрузки с неповторяющимися шаблонами он только платит за вытеснение.
  Недиагностируемость закрыта тем же: `templateCacheSize` отличает «кэш мал» от «шаблоны не
  повторяются».

### M3. Precision текста не имеет потолка — VM/JS расхождение

  ```

  ```
- Шаблон, отвергнутый на сервере, молча проходит в вебе.
- **Статус: исправлено 2026-08-08.** `_readDecimal` больше не полагается на то, что `int.tryParse`

### M8. `CharSink` в ~29 раз медленнее `StringBuffer` на многострочном выводе

- **Статус: исправлено для веба 2026-08-07, на VM оставлено как было.** Профилирование
  показало, что вопрос не «`Uint16List` или `StringBuffer`», а «какая платформа». На один
  результат в 16 юнитов:

  | | VM | dart2js | dart2wasm |
  |---|---|---|---|
  | паттерн `CharSink` | **45.2** | 573.6 | 274.7 |
  | `StringBuffer` | 89.3 | **4.1** | **25.1** |

  На VM типизированный массив выигрывает вдвое, на обеих веб-целях проигрывает — в 140 и
  в 11 раз. Поэтому `CharSink` ветвится по `bool.fromEnvironment('dart.library.js_interop')`:
  константа сворачивается на этапе компиляции, каждая цель оставляет одну ветку.

  Предикат выбран не `identical(1, 1.0)`: тот означает «int представлен как double», то есть
  строго dart2js, и на dart2wasm даёт `false` — правка прошла бы мимо wasm с его
  одиннадцатикратным штрафом. Проверено запуском на всех трёх платформах.

  Литерал-op хранит **оба** представления и читает своё: попытка оставить только `String`
  просадила VM на 50 % (78 → 117 нс), потому что `setRange` из `Uint16List` — блочное

  (`printf_formatter.dart:261-301`, `binary64.dart:83-102`): `%.0a` на 1.5 → `0x2p+0` против
  `0x1p+0` у libc. Наш результат согласуется с glibc-семантикой, но в реестре расхождений
  задокументирована только нормализация субнормалей, не округление.

  Расхождение подтверждено замером на этой машине, но описано в отчёте неточно, и в двух местах.

  Первое: «Apple libc — иначе» звучит как другое правило округления; на деле libc расходится
  только на **ровных половинках**. Прогон обеих реализаций по одним значениям:

  | значение | наше | Apple libc |
  |---|---|---|
  | `%.1a` 0x1.28 (ничья вниз к чётному) | `0x1.2p+0` | `0x1.2p+0` |
  | `%.1a` 0x1.08 (ничья вниз к чётному) | `0x1.0p+0` | `0x1.0p+0` |
  | `%.1a` 0x1.18 (ничья вверх к чётному) | `0x1.2p+0` | `0x1.1p+0` |
  | `%.1a` 0x1.38 (ничья вверх к чётному) | `0x1.4p+0` | `0x1.3p+0` |
  | `%.1a` 0x1.f8 (ничья с переносом) | `0x2.0p+0` | `0x1.fp+0` |
  | `%.0a` 1.5 | `0x2p+0` | `0x1p+0` |
  | `%.0a` 1.75, 2.5, 1.25, 1.0625 | совпадает | совпадает |

  Совпадение ровно там, где ничья округляется вниз, и расхождение ровно там, где вверх, — это
  подпись усечения ничьих у libc против nearest-even у нас. Всё, что ничьёй не является,
  округляется одинаково.

  Второе: опора на glibc в отчёте («наш результат согласуется с glibc-семантикой») здесь
  непроверяема — Linux-окружения на машине нет, контейнеров тоже. Ссылаться поэтому стоит не на
  чужую реализацию, а на стандарт: корректное округление `%a` при явной precision — recommended
  practice, а не требование, и «корректное» означает «по текущему направлению округления», чей
  умолчательный режим — nearest-even. То есть наше поведение следует рекомендации, а libc ей не
  следует, оставаясь при этом соответствующей.

  Исправлено: в реестр расхождений добавлена запись `hexadecimal-tie-rounding` с исполняемым

# Architecture review

## Сильные стороны

**Двухпутёвая архитектура сделана правильно.** Главный риск «быстрый путь разошёлся с медленным»
закрыт четырьмя механизмами: (1) компиляция **тотальна** — `_compileBraceProgram`/`_compilePrintfProgram`
никогда не бросают, всё непокрытое становится fallback-op'ом, дословно исполняющим legacy;
(2) классификатор **зондирует** настоящие валидаторы (`_rejectsDartDoublePrecision`,
`_rejectsHotDouble` — `template_ir.dart:585-613` вызывают валидатор в try/catch), поэтому правило
физически не может разъехаться с горячим путём; (3) legacy сохранён как исполняемый оракул
(`debugFormatBraceWithoutIr`/`debugFormatPrintfWithoutIr`); (4) паритет проверяется дифференциальным
фаззингом с exhaustive-сравнением полей контекста ошибок, а не только строк. Два независимых прохода
по ~640 000 пар (включая суррогаты, комбинирующие знаки, юникод-цифры, 7 конфигураций движка) не
нашли ни одного расхождения — это редкий результат.

**Иммутабельность и ортогональность конфигурации.** Переход от глобальных мутабельных регистров 2.0
к иммутабельному `Format` доведён до конца: защитное копирование коллекций, валидация на входе
(четыре независимые проверки с отдельными `reason`), «one source of truth» для зарезервированных
имён (`format.dart:157-158`). Семь осей настройки не пересекаются.

**Кэш параметризован корректно.** Это я проверил лично, потому что два прохода дали разные оценки:
ключ — только строка шаблона, и это правильно. AST от конфигурации не зависит; `TextUnit` разведён
двумя слотами программ и спецификаций; `doubleFormatMode`, `numberLocale`, `formatters` читаются из
движка в рантайме. Оба порядка (SDK-первым и compatible-первым) дают корректные различающиеся
результаты:

```
sdk-first   : 3|1e+0  затем  2|1.000000e+00
compat-first: 2|1.000000e+00  затем  3|1e+0
```
Гипотеза «первый вызов задаёт профиль для последующих» **не подтвердилась**.

**Реентерабельность.** Общего мутабельного буфера нет: `CharSink` создаётся на вызов, `_FieldResolver` —
на процессор, курсор printf — на процессор. Кастомный форматтер, рекурсивно вызывающий `format()`
(в т.ч. с тем же шаблоном), и форматтер, вытесняющий исполняемый шаблон из кэша прямо во время
исполнения, дают корректный вывод.

## Слабые места и спорные решения

**Кэш — глобальное состояние на уровне библиотеки, без публичного управления.** Это одновременно
источник M5 (память), H6 (обрыв на 513), и невозможности диагностики. Для библиотеки, где шаблоны
могут приходить из внешних данных (сообщения из БД/конфига), отсутствие настройки ёмкости и `clear()`
— архитектурный пробел, а не мелочь.

**Гейты `identical(...)` как механизм выбора горячего пути** (M6) — хрупкое решение: семантически
идентичная конфигурация молча теряет оптимизацию, и ни один тест паритета этого не поймает, потому
что вывод не меняется. Такие гейты должны опираться на предвычисленное свойство движка, а не на
идентичность канонизированной константы.

**`CharSink` оптимизирован под одну ось.** Дизайн «всё в `Uint16List`» выигрывает на коротких
числовых выводах и катастрофически проигрывает на строковых (M8). Это осознанный размен, но он не
задокументирован как размен, и `_single` спасает только вырожденный случай.

**Три копии числового layout'а** (M18) — прямое следствие того, что IR транслитерировал legacy
вместо того, чтобы вынести общее ядро. Комментарии-контракты («это транслитерация такой-то строки
legacy») смягчают риск, но не устраняют его.

**Асимметрия защитных политик.** Потолок `_maximumSafeFormatOption` применяется к ширине в обоих
диалектах и к precision в printf, но не к precision текста в brace (M3) и не к числовому индексу
(H3). Политика есть, покрытие неполное.

## Архитектурные риски

1. Кэш как канал удержания памяти и управляемой извне деградации при внешних шаблонах.
2. Замороженная арность 10 в типе tear-off (L12) — изменение станет breaking.
3. Второй неофициальный вход `package:format/src/engine.dart` (L29): пользователи такие входы находят,
   и потом любое изменение внутренней библиотеки становится де-факто breaking.
4. Дизайн-документы разошлись с кодом в пяти местах (L17) — они уже перестали быть надёжным
   источником истины.

# Testing review

## Что покрыто, и покрыто хорошо

**Внешние эталоны как источник истины.** Фикстуры сгенерированы CPython 3.14 и C++23/libc, с
зафиксированными версиями генератора прямо в JSON и тестом, пиннящим их
(`test/python_compatibility_test.dart:15-18`); генератор отказывается работать не на CPython 3.14
(`tool/generate_python_fixtures.py:217-218`).

**Исполняемые реестры расхождений** — лучшая часть тестовой стратегии. Каждое документированное
отличие от Python/C++ обязано иметь работающий пример, иначе тест падает
(`python_compatibility_test.dart:151-159`, `sprintf_compatibility_test.dart:68,75`). Это устраняет
главный класс рассинхронизации «документация против кода».

**Один `test()` на фикстуру** вместо цикла внутри одного теста, с явным комментарием, почему именно
так — регрессия в одном кейсе не прячет остальные.

**Exhaustive `switch` без `default`** над sealed-иерархией ошибок (`test/parity_harness.dart:147-165`) —
новый тип исключения ломает компиляцию тестов, а не тихо выпадает из сравнения.

**Anti-degeneracy гарды в фаззере** (`test/template_ir_fuzz_test.dart:208,253-257`) — счётчик реально
отрендеренных кейсов, а не только уникальных шаблонов. Это защита от самого коварного вида гниения
фазз-тестов («зелёный корпус из одних ошибок»).

**Гигиена тестов образцовая.** Проверено специально: ни одного `skip:`, `solo:`, закомментированного
`test(`, ни одного `throwsA(isA<Exception>())` — все 90+ `throwsA` типизированы конкретными классами.
Глобальное состояние (кэш) сбрасывается в `setUp` во всех четырёх файлах, которые его трогают.

   `double_format_test`, `conversion_test`, `integer_format_test` — VM-only де-факто. Именно поэтому

   но регресс в них проектный набор не поймает.
7. **Реестр Python-расхождений валидируется формально** (M10): 10 из 12 якорей битые, и тест это

# Performance and reliability

## Производительность

Template IR — настоящий и большой выигрыш: против Format 2.0 горячие сценарии дают geometric mean
≈0.12, против sprintf 7.0 ≈0.10, то есть 8–30× на массовых путях. Но выигрыш неравномерный, и «ямы»
находятся ровно в обычных сценариях:

| Сценарий | Замедление | Находка |
|---|---|---|
| Группировка разрядов `{:,d}`, `{:,.2f}`, `{:010,d}` | ×4.5 … ×14.5 | M17 |
| Многострочный вывод против `StringBuffer` | ×29 | M8 |
| `compatible`-профиль для `{}` | ×9 | M7 |
| 513-й шаблон в рабочем наборе | ×7, навсегда | H6 |
| `Format(numberLocale: CNumberLocale())` без `const` | ×3.4 | M6 |
| Маршалинг аргументов в `sprintf('%d', 42)` | 41 % стоимости | L11, L12 |

Ни одну из этих ям текущие гейты не увидят: все они укладываются в запас ×3–×10 (H4).

## Конкурентность и жизненный цикл

Гонок нет и быть не может: кэши — top-level `final` переменные, то есть per-isolate, а Dart-изоляты
не делят память. Мутируемое состояние (`_scalarProgram`/`_graphemeProgram`, `_scalarSpec`/`_graphemeSpec`,
`_staticResolved`, `_staticContext`) записывается идемпотентно и детерминировано по (строка, TextUnit).
Асинхронности в библиотеке нет вовсе — весь код синхронный, что снимает целый класс рисков.

Состояние при исключении остаётся согласованным: исключение выбрасывает недописанный `CharSink`,
мемоизируются только успешные результаты, следующий вызов даёт корректный вывод. Это проверено
серией исключений из пользовательского кода — дрейфа нет.

## Управление ресурсами

Настоящих утечек нет — Dart с GC, а кэш ограничен. Но **удержание** памяти неограниченно по объёму
(M5): 512 записей × произвольный размер шаблона × коэффициент 5.5. В связке с H6 (управляемая извне
деградация ×7) это делает глобальный кэш главной точкой риска при внешних шаблонах.

## Надёжность

~1.3 млн вызовов фаззинга на случайных шаблонах под `--enable-asserts`, в трёх конфигурациях движка,
с аргументами включая `List`, `Map`, `BigInt`, `nan`, `null`, не дали ни одного не-`FormattingException`
из путей форматирования. Единственная утечка нетипизированного исключения — в конструкторе (H2).
Переполнение стека невозможно: глубина рекурсии парсера жёстко ограничена двумя уровнями
(`brace_parser.dart:52-58`). Инъекции синтаксиса через вложенную спецификацию нет: значение,
подставленное в `{:{}}`, парсится только как спецификация.

# Maintainability

**Что помогает сопровождению.** Комментарии объясняют «почему», а не «что», и почти каждая
нетривиальная ветка `template_ir.dart` помечена тем, какую строку legacy она транслитерирует и почему
порядок ветвлений — контракт (`:92-99`, `:221-226`, `:433-437`, `:1054-1061`, `:1304-1305`). Это ровно
то, что нужно, чтобы через полгода никто не «упростил» порядок проверок. `analysis_options.yaml`
исключительно строгий (10.8 KB, `strict-casts`/`strict-inference`/`strict-raw-types` + десятки
включённых правил), и при этом `dart analyze --fatal-infos lib test example` даёт ноль замечаний.

**Что мешает.** `template_ir.dart` — 1594 строки с тремя дословными дублями обвязки и тремя копиями
писателя выравнивания (M18); при правке правил `*`-опций нужно три синхронных изменения.
`_parseFormatSpecGeneral` (`format_spec.dart:46-169`) — 124 строки и 13 мутабельных локальных
переменных; `_parseNodes` (`brace_parser.dart:23-111`) — 89 строк, 4 уровня вложенности, три разных
исхода `}` в одном блоке. `_readDecimal` (`format_spec.dart:389-404`) содержит теневую переменную,
затеняющую захваченную замыканием, — работает, но читается плохо.

**Технический долг, ранжированный по цене отказа:**

1. Инфраструктура публикации (H1, M11) — блокирует релиз.
2. Пороги и подключение гейтов (H4, H5) — долг «защита есть на бумаге, но не работает».
3. Дублирование числового layout'а (M18) — растёт с каждой оптимизацией IR.
4. Расхождение дизайн-документов с кодом (L17) и HANDOFF.md на 79 KB (L27) — документация уже
   перестала быть надёжной.
5. Мёртвый код (L2) — восемь мест, каждое дёшево удалить, но они маскируют реальную сложность.

# Positive findings

- **Численная корректность на уровне, редком для этой задачи.** Ноль расхождений с CPython на
  ~1.95 млн кейсов и ноль с C `printf` вне `%a` на ~1.48 млн. `Binary64` даёт точную десятичную
  развёртку без потерь, `roundDecimal` — настоящий half-even на точных рациональных.
- **Fast path не жертвует корректностью.** `_formatFixedFast` (`number_format.dart:334-348`) детектирует
  ties честно; `_formatIntMagnitude` использует `substring(1)` вместо `-value`, снимая переполнение
  на `minInt`.
- **Зондирование валидаторов вместо копирования правил** (`template_ir.dart:585-613`) — приём, который
  делает рассинхронизацию быстрого и медленного пути физически невозможной. Это лучше любого
  комментария «держите в синхроне».
- **Консервативный классификатор**: не уверен — на legacy. Именно поэтому 640 000 дифференциальных
  пар прошли без единого расхождения.
- **Sealed-иерархия ошибок с исчерпывающим `switch` в `toString()`** (`errors.dart:51,62-93`): новый
  подкласс не скомпилируется, пока не будет добавлен, — payload физически не может остаться
  нерапортованным.
- **Диагностика защищена от враждебных значений**: `_describeGuarded` (`errors.dart:34-44`) не доверяет
  `toString()` payload'а и откатывается к `Error.safeToString`. Контекст ошибки с шестью полями даёт
  сообщения, по которым баг чинится без отладчика.
- **Единый guard-паттерн вокруг пользовательского кода** в шести местах с сохранением оригинального
  `stackTrace` через `Error.throwWithStackTrace`. Из ~140 враждебных сценариев наружу пробилось ровно
  одно исключение (H2).
- **Защита от циклов в `!r`** через identity-set с корректным `finally`-снятием отметки.
- **Явная и последовательная работа с web-семантикой int** (`template_ir.dart:4-13`) с обоснованием
  «работаем в отрицательном пространстве, чтобы minInt не переполнился». Все найденные web-дыры — там,
  где эта дисциплина **не** применялась.
- **`_sealedInDebug`** (`brace_ast.dart:29-40`): неизменяемость AST проверяется под asserts, но не
  стоит ничего в проде, с отдельным сеймом для проверки самой проверки.
- **Correctness-first бенчмарк**: кандидат и база сверяются с руками написанным ожиданием **до** старта
  секундомера (`runner.dart:178-195`) — харнес не может измерять неправильный вывод. Медиана вместо
  среднего, geometric mean для агрегации, чередование кандидата и базы по чётности раунда, правило
  «падаем только при нарушении в обоих прогонах», честная классификация несравнимых сценариев как
  `informational`, и валидация отчётов, которую нельзя обойти правкой одного поля.
- **`benchmark/suite/lib/src/template_ir_benchmark.dart`** — образцовый A/B-бенчмарк: checksum против
  DCE, сверка с эталоном, чередование IR/legacy, отдельные fallback-контроли.
- **Замороженные базы** с обоснованием: `sprintf: 7.0.0` точным пином и комментарием «bumping
  invalidates comparability».
- **README честный.** Все 26 точных примеров сошлись до символа, включая тонкие места (границы
  точности SDK, оба double-профиля, переход `f` в экспоненциальную форму на `1e21`). README не скрывает
  неудобного: прямо признаёт неоднозначность `{}` для пустых `Map`/`Set` и оговаривает пределы вывода
  о производительности.

# Отвергнутые гипотезы

Фиксирую отдельно — это тоже результат ревью:

- **`% d` (флаг пробела) якобы не поддерживается.** Опровергнуто прямым запуском:
  `sprintf('% d', 1)` → `" 1"`. README не обязан упоминать его в списке пропусков.
- **Кэш якобы небезопасен между движками с разными профилями.** Опровергнуто: оба порядка
  (`sdk`-первым и `compatible`-первым) дают корректные различающиеся результаты; то же для `TextUnit`.
- **Расхождение IR и legacy.** Не найдено ни одного на ~640 000 дифференциальных пар в двух
  независимых проходах (включая сравнение полей контекста исключений, а не только строк).
- **DoS по ширине в brace-пути.** Закрыто: `format_spec.dart:91-98` отвергает `width > 100000`.
- **Переполнение стека на вложенности.** Невозможно: глубина рекурсии ограничена двумя уровнями.
- **Инъекция синтаксиса шаблона через вложенную спецификацию.** Значение никогда не
  переинтерпретируется как синтаксис.
- **Zero-padding нефинитных double** (`{:010f}` на `inf` → `0000000inf`). Выглядит как баг, но CPython
  делает ровно то же; brace верен для Python, printf — для C.
- **Гонки/утечки в кэше.** Кэши per-isolate, Dart-изоляты не делят память; мемоизация идемпотентна.

# Непроверенные предположения

- Влияние M16 (`10^100000` без кэша) — тайминг `{:.50000f}` не снимался.
- M21 (`-0.0 is int` на dart2js) — прямых ассертов нет, ветка проверена только чтением.
- Причина исключения брейсов из JS-матрицы бенчмарков (M19) — в документации не найдена; возможно,
  есть техническое ограничение (Format 2.0 baseline под dart2js).
- Рантайм-поведение `IntlNumberLocale` — тесты `packages/format_intl/test/*` в этом ревью не
  запускались; проверена только конфигурация подпакета.
- Заявление README о превосходстве `dartSdk`-профиля (`README.md:105-110`) бенчмарком не
  перепроверялось.
