# Project overview

`format` — Dart-пакет форматирования строк с brace- и printf-синтаксисом. Поток:
публичный API → разбор и кэш шаблона → IR для `TextUnit` → вывод через
`CharSink`. Есть расширения, локали чисел, ограниченный per-isolate кэш и
отдельный пакет `format_intl`.

# Medium and low-severity findings

## M1 — числовые лимиты срабатывают после выделения памяти под весь токен

- Severity: Medium
- Файлы: `lib/src/format_spec.dart:35–42,58–75,114–138,325–337,440–452`;
  `lib/src/brace_parser.dart:277–294,332–397,399–436`
- Проблема: длинные width/precision и числовые индексы сначала превращаются в
  `List<String>`/`List<int>`, и лишь затем проверяются потолки. Например,
  `format('{:' + '9' * N + 'd}', 1)` создаёт список из N элементов до отказа по
  ширине; `format('{' + '9' * N + '}', 1)` аналогично создаёт список цифр до
  проверки 19-значного индекса. Последовательность из N нулей может вообще
  считаться индексом `0`, но всё равно требует линейной промежуточной памяти.
- Сценарий: шаблоны поступают из HTTP, БД или пользовательского ввода; атакующий
  передаёт многомегабайтный числовой токен.
- Последствия: существенное дополнительное потребление памяти и риск OOM/DoS до
  контролируемой `FormatException`; лимит кэша не ограничивает эту временную
  аллокацию.
- Направление исправления: выполнять потоковое сканирование цифр и проверять
  длину/потолок до материализации списка; после достижения лимита только найти
  границу токена для точной диагностики.
- Уверенность: high

**Вердикт: закрыт частично 2026-08-13, и механизм в находке назван неточно.**
`_readDecimal` (`format_spec.dart`) цифры не накапливает — он считает
арифметикой с потолком, это правка от 2026-08-11; O(N) там даёт
`_specificationUnits`, материализующий спецификацию списком единиц, и это
константное усиление над текстом, который вызывающий и так держит в памяти.

А для **индекса поля** находка верна буквально, и это исправлено:
`_readDecimalDigits` (`brace_parser.dart`) теперь отбрасывает ведущие нули по
ходу чтения и не кладёт значащие цифры сверх того, чем индекс может быть,
продолжая при этом дочитывать токен до конца — чтобы он кончался там же, где
кончался, и ошибка по-прежнему указывала на него целиком. Проверено, что
поведение не поехало: `{0}`, `{000}`, пять тысяч нулей и пять тысяч нулей с
единицей читаются как прежде, а слишком широкие прогоны по-прежнему
отвергаются.

**Вердикт: закрыт 2026-08-13.** Dartdoc `Formatter.specifier` переписан:
геттер читается один раз, при конструировании `Format`, и там же
валидируется. Дописано и то, чего в находке не было: обёрнутый отказ не несёт
места в шаблоне, потому что шаблона на тот момент ещё нет — проверено
исполнением, `context.template` и `context.offset` равны `null`. Поведение не
менялось: его пинит тест `formatter_registry_test.dart:190`.

## L1 — Dartdoc `Formatter.specifier` противоречит фактическому контракту

- Severity: Low
- Файлы: `lib/src/extensions.dart:32–38`; `lib/src/format.dart:46–65,190–197`;
  подтверждающий тест `test/formatter_registry_test.dart:190–203`
- Проблема: Dartdoc утверждает, что getter `specifier` читается при разрешении
  placeholder и ошибка возникает при форматировании. Реализация читает его при
  `Format(...)`, что также явно проверено тестом.
- Сценарий: автор расширения или потребитель API рассчитывает отложить ошибку
  getter до первого вызова `format`.
- Последствия: неверное ожидание жизненного цикла и места обработки исключения.
- Направление исправления: исправить Dartdoc: getter читается ровно один раз при
  конструировании для валидации и построения неизменяемого индекса.
- Уверенность: high

# Architecture review

Границы публичного API, разбора, исполнения IR, локалей и кэширования в целом
ясны. Кэш корректно изолирован по isolate, а форматирование синхронно;
подтверждённых race condition или утечек ресурсов не найдено. Использование
единой библиотеки с `part` повышает внутреннюю связанность, но дифференциальные
тесты IR против legacy-пути заметно снижают риск регрессий.

# Performance and reliability

Новые замеры производительности не интерпретировались из-за параллельной
нагрузки на машину. По коду видны разумные меры: ограничение кэша по числу
записей и оценке памяти, bypass для холодных потоков, специализированный вывод
для платформ. M1 остаётся исключением: кэш не защищает от временных аллокаций до
разбора некорректного шаблона.

# Maintainability

Код проходит строгий анализ, публичные ошибки типизированы, а конфигурация
снапшотится при создании `Format`. Документация в основном соответствует
реализации; L1 — точечное исключение. Самые сложные участки — parser/IR/числовое
форматирование — хорошо защищены parity и fuzz-тестами.

# Positive findings

- Проверки проходят на VM, dart2js и dart2wasm.
- Публичный API аккуратно отделён от внутренностей.
