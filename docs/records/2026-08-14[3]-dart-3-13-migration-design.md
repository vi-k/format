# Миграция внутренних инструментов на Dart stable

Статус: исполнен частично 2026-08-14: код и CI мигрированы, целевые сторожа и
полный локальный stable-прогон зелёные; commit, CI и AMD-эталон ещё открыты.
Источником истины для wasm-host'ов служат `benchmark/wasm_host.mjs` и
`benchmark/suite/tool/run.dart`, для версии CI — `.github/workflows/ci.yaml`.

## Контекст

Репозиторий временно закреплён на Dart 3.12.2. Причиной был переход
dart2wasm-loader'а в Dart 3.13.0 на новый API: прежде функции `compile`,
`instantiate` и `invoke` экспортировались рядом, теперь `compile` возвращает
`CompiledApp`, у которого вызывается `instantiate`, а полученный
`InstantiatedApp` предоставляет `invokeMain`.

Внешний блок уже снят: текущий `package:test` 1.31.2 проходит полный
dart2wasm-набор под Dart 3.13.0. Внутри репозитория старый протокол остался в
двух местах: в закоммиченном host'е performance gate и в host'е, который
benchmark suite строит во временном каталоге. Форматтер 3.13 расходится с
репозиторием в одном файле — `benchmark/test/benchmark_scenarios_test.dart`.

## Цель и границы

Миграция должна одним изменением:

- перевести оба внутренних wasm-host'а на loader API Dart 3.13;
- вернуть все основные CI jobs с точного 3.12.2 на движущийся `stable`;
- принять форматтер текущего stable;
- подтвердить работу пакета, host'ов и benchmark suite полным списком проверок
  из `docs/handoff.md` уже на stable;
- убрать исполненную миграцию из открытого списка handoff.

Публичный API и поддерживаемый пол пакета не меняются. Проверка Dart 3.7.2 в
матрице `checks` остаётся. Поддерживать старый loader API 3.12 во внутренних
инструментах после миграции не требуется: они запускаются только основным SDK
репозитория.

## Выбранный подход

Оба host'а переходят прямо на протокол 3.13:

1. `compile(bytes)` возвращает скомпилированное приложение;
2. `compiled.instantiate({})` возвращает экземпляр;
3. `instance.invokeMain(...args)` передаёт аргументы Dart-функции `main`.

Ошибки не перехватываются: top-level `await` и процесс Node уже превращают
ошибку компиляции, инстанцирования или вызова в ненулевой exit code. Это тот же
контракт отказа, который есть сейчас.

Compatibility shim для 3.12/3.13 не нужен. Он добавил бы ветвление в
измерительный harness ради SDK, которым harness больше не запускается.
Генерировать committed host на лету тоже нельзя: performance gate обязан
исполнять проверенную часть репозитория, а не дописывать измерительную оснастку
во время запуска.

## Изменения по компонентам

### Wasm-host'ы

`benchmark/wasm_host.mjs` импортирует из соседнего loader'а только `compile`,
а затем вызывает методы возвращённых объектов. Разбор пути к модулю, поиск
loader'а рядом и передача аргументов сохраняются.

Строка host'а в `benchmark/suite/tool/run.dart` использует тот же протокол.
Host остаётся генерируемым, потому что он обязан ссылаться на только что
созданные `benchmark.wasm` и `benchmark.mjs` во временном каталоге.

### CI

В `.github/workflows/ci.yaml` основная запись матрицы `checks` и отдельные jobs
`generated-artifacts`, `coverage`, `benchmark-suite`, `performance-gate`
переходят с `'3.12.2'` на `stable`. Запись минимального SDK `'3.7.2'` и флаг
`primary` сохраняются, поэтому смена текста версии не может молча выключить
шаги основного SDK.

Комментарии про временный пин и внешний блок удаляются или переписываются как
текущее правило: репозиторий форматируется и полностью проверяется на stable,
а нижняя граница проверяется отдельно.

### Версия компилятора в исполняемых тестах

Два теста в `benchmark/test/benchmark_scenarios_test.dart` действительно
компилируют JS и Wasm текущим `Platform.resolvedExecutable`. Они должны
передавать в `format.benchmark.dartCompilerVersion` версию этого executable,
а не литерал `3.12.2`, и затем ожидать ту же строку в отчёте.

Литералы `3.12.2` и `3.12.3` в `benchmark_gates_test.dart` остаются: там это
намеренно разные фиктивные окружения, которыми проверяется сопоставимость
отчётов, а не описание SDK репозитория.

### Форматирование и handoff

Форматирование применяется ко всему репозиторию текущим stable. По разведке
меняется только `benchmark/test/benchmark_scenarios_test.dart`; этот факт не
является предположением о будущих версиях, поэтому перед коммитом всё равно
форматируется всё дерево.

`docs/handoff.md` после исполнения называет stable основным SDK, переносит
миграцию в сделанное и удаляет её из `## Что открыто`. Новый пункт владельца
про медленный `c` под JavaScript остаётся следующим отдельным делом.

## Проверка

Красная фаза использует существующие интеграционные сторожа, а не новый seam:

- тест `compiled wasm runner records dart2wasm provenance` компилирует
  настоящий модуль и запускает committed `benchmark/wasm_host.mjs`; со старым
  host'ом под 3.13 он не может импортировать `instantiate`;
- wasm-прогон benchmark suite компилирует настоящий модуль и запускает host,
  созданный `tool/run.dart`; со старой строкой он падает тем же образом.

После правки обе проверки должны стать зелёными. Затем на stable выполняется
целиком раздел `## Как проверить всё` из `docs/handoff.md`: форматирование,
анализ, три полных рантайма тестов, вспомогательные тесты, `format_intl`,
самостоятельный архив, генераторы, покрытие, тесты suite и три quick-матрицы.

## Performance gate и эталон

Матрица сценариев не меняется, поэтому миграционный коммит не переписывает
эталон вслепую. Однако эталон записан на Dart 3.12.2, и отчёты stable будут
несопоставимы с ним по окружению. После push миграционного коммита нужно
запустить workflow `performance-gate`. Первый подходящий прогон на AMD
записывает новый эталон отдельным follow-up-коммитом по правилам
`benchmark/results/README.md`; отчёты должны принадлежать точной ревизии,
поэтому включить этот файл в предшествующий миграционный коммит невозможно.

До новой записи `comparable: false` — ожидаемое состояние, но не завершение
follow-up: ночной гейт снова принимает решения только после эталона stable.

## Порядок коммитов и критерий завершения

1. Эта согласованная спецификация — отдельный документальный коммит.
2. Host'ы, CI, динамическая версия тестов, форматирование и handoff — один
   атомарный миграционный коммит после полного зелёного прогона на stable.
3. Новый AMD-эталон — отдельный follow-up после CI-диспатча и проверки
   ревизии отчётов.

Миграция завершена, когда миграционный коммит прошёл локальный полный список и
обычный CI на stable. Инфраструктурный follow-up завершён, когда записан и
проверен сопоставимый эталон stable. Только после этого следующим делом берётся
исследование `c` под JavaScript.
