# Единый источник справочника форматов

Статус: согласован в диалоге и прошёл self-review 2026-08-14; записанная версия
ждёт проверки владельцем перед планированием реализации.

## Контекст

Корневой `README.md` уже перечисляет presentation types фигурного диалекта и
conversion types `sprintf`, а последующие разделы объясняют отдельные темы:
Unicode, числовые локали, профили `double`, расширения и intentional
расхождения с Python и C. Этого хватает для знакомства с пакетом, но не для
использования мини-языков как справочника. Чтобы узнать точный порядок опций,
матрицу допустимых флагов, поведение `*` или границы ширины и точности,
разработчику приходится читать парсеры и тесты.

Простое расширение двух README вручную решило бы навигацию, но создало бы ещё
одну независимо редактируемую копию контракта. Уже сейчас правила находятся в
нескольких местах реализации: фигурная грамматика — в `brace_parser.dart` и
`format_spec.dart`, printf-грамматика и флаги — в `printf_parser.dart`, а
применимость опций и типов — в форматтерах значений. Полное ручное описание
неизбежно начало бы отставать.

Нужен один машиночитаемый публичный контракт, который одновременно строит
справочник и проверяет поведение движка, не переводя production hot path на
новую универсальную модель.

## Цели

- Дать в корневом README самостоятельный полный справочник обеих
  мини-грамматик: `{...}` и `sprintf`.
- Хранить точные множества типов, опций, сочетаний, пределов и проверочных
  примеров в одном каталоге.
- Генерировать из одной семантики английскую и русскую reference-секции.
- Исполнять каталог через публичный API и ловить расхождение документации с
  реализацией обычным обязательным прогоном.
- Ловить добавление нового встроенного brace type, printf conversion или
  допустимого printf-флага без обновления каталога.
- Сохранить нынешнюю архитектуру и производительность парсеров.

## Не входит в работу

- Изменение синтаксиса или поведения форматирования.
- Объявление Python или C полным нормативным контрактом пакета.
- Генерация всего README: введение, руководства, миграция и объяснения сложных
  тем остаются написанными человеком.
- Полный каталог каждого возможного ошибочного шаблона и точного текста каждой
  ошибки. Справочник описывает классы отказов и правила, а не бесконечное
  множество неправильных строк.
- Перевод production-парсеров на data-driven interpreter.
- Изменение версии, публикация или performance baseline.

## Решение

### Нормативный contract-каталог

В `tool/src/format_reference_contract.dart` появится типизированный const-каталог.
Он является единственным редактируемым источником точных данных справочника и
не импортируется production-библиотекой.

Каталог разделён на небольшие сущности с одной обязанностью:

- `DialectContract` собирает одну мини-грамматику;
- `GrammarRule` задаёт форму конструкции и её ограничения;
- `OptionContract` описывает токен, позицию, смысл, default и применимость;
- `TypeContract` описывает presentation/conversion type, принимаемую категорию
  Dart-значений, разрешённые опции и важные особые случаи;
- `ConformanceCase` задаёт вызов публичного API и ожидаемый результат либо
  точный класс `FormattingException`;
- `LocalizedText` содержит английскую и русскую подпись одного семантического
  идентификатора.

Точные имена классов разрешено уточнить в implementation plan, но граница
остаётся этой: семантические множества и связи записываются один раз, переводы
не несут отдельной логики.

Каталог не должен хранить свободный большой prose-текст. Длинное объяснение
округления, Unicode или локали останется в ручном разделе README; строка
каталога содержит краткое правило и ссылку на его якорь. Это удерживает
машиночитаемую часть обозримой и не превращает генератор в шаблонизатор всей
документации.

### Почему каталог не управляет runtime

Фигурный и printf-парсеры имеют измеренные специализированные fast paths,
стриминговый разбор длинных числовых опций и скомпилированный template IR.
Замена их общим табличным интерпретатором расширила бы задачу и создала риск
регрессии ради документации.

Вместо этого каталог задаёт публичный контракт, а параметризованные тесты
доказывают соответствие реализации. Небольшие read-only debug-seams открывают
тестам фактические конечные множества из parser-кода. Они находятся только в
`package:format/src/engine.dart`, не экспортируются поддерживаемым facade и не
участвуют в форматировании.

## Что именно документируется

### Фигурный диалект

Reference-секция описывает весь путь от шаблона до presentation:

1. Литералы и экранирование `{{`/`}}`, включая особое требование баланса внутри
   format specification.
2. Replacement field с автоматическим, позиционным или именованным корнем.
3. Последовательности `.attribute` и `[item]`, правила идентификаторов и
   несовместимость автоматической и ручной нумерации.
4. Конверсии `!s`, `!r`, `!a` и их место перед `:format_spec`.
5. Вложенное replacement field в specification и предел глубины.
6. Форму format specification в точном порядке:
   `[fill]align`, `sign`, `z`, `#`, `0`, `width`, целочисленную grouping,
   точку с precision либо fractional grouping, затем встроенный type или
   custom formatter с необязательным payload.
7. Токены каждой опции, default, применимость и взаимодействия: например,
   numeric `=` alignment, текстовый запрет `0`, поведение `z`, alternate form,
   `,`/`_`, диапазоны precision и границы безопасной ширины.
8. Полную матрицу встроенных types без типа, `s`, `d`, `b`, `o`, `x`, `X`,
   `c`, `n`, `f`, `F`, `e`, `E`, `g`, `G`, `%`: принимаемые Dart-типы,
   поддержанные опции, default precision и ссылка на углублённое объяснение.
9. Выбор custom formatter по имени или пустой specification, синтаксис имени
   и payload, а также какие layout-опции движок применяет сам.

Грамматика в README — читабельная EBNF-подобная запись. Это документационная
нотация, не новый parser input и не обещание экспортировать grammar API.

### Printf-диалект

Reference-секция отдельно описывает:

1. Литеральный текст, `%%` и conversion token вида
   `%[flags][width][.precision]conversion`.
2. Флаги `-`, `+`, space, `#`, `0`, возможность повторов и фактический
   приоритет конфликтующих флагов.
3. Литеральные width/precision и `*`, порядок потребления динамических опций и
   основного значения, отрицательную width как left alignment и отрицательную
   precision как отсутствие precision.
4. Полную матрицу `%s`, `%c`, `%d`, `%i`, `%u`, `%o`, `%x`, `%X`, `%f`, `%F`,
   `%e`, `%E`, `%g`, `%G`, `%a`, `%A`, `%%`: принимаемые значения, допустимые
   флаги, width/precision и default.
5. Отказ от positional `$` и length modifiers, правила ASCII-цифр, безопасные
   пределы и классы ошибок.
6. Отличия integer и floating conversions по принимаемому Dart-типу и ссылки
   на разделы про Dart/compatible double profiles, Unicode и локали.

### Ошибки

Таблицы различают четыре полезных для разработчика случая:

- грамматически неправильный шаблон — `InvalidFormatException`;
- известная конструкция с недопустимой комбинацией опций —
  `InvalidSpecifierException`;
- conversion/type не умеет переданное значение —
  `UnsupportedFormatValueException` либо `UnsupportedConversionException` в
  соответствующем пути;
- не хватает аргумента — `MissingFormatArgumentException`.

Точный выбор класса для каждой строки закрепляет conformance-case. Текст
сообщения не становится частью генерируемой матрицы, кроме уже отдельно
обещанных полей `FormatExceptionContext`.

## Структура README

В `README.md` появляется канонический раздел `Format reference`, в
`README.ru.md` — его русская проекция. Каждый заключён между уникальными
HTML-комментариями начала и конца. Генератор владеет всем содержимым между
маркерами; ручные изменения внутри блока запрещены и будут перезаписаны.

Порядок подразделов одинаков в обоих языках:

1. brace template grammar;
2. brace format specification;
3. brace options;
4. brace presentation matrix;
5. printf grammar and dynamic options;
6. printf flag matrix;
7. printf conversion matrix;
8. limits and error classes.

Нынешние таблицы `Presentation types` и printf conversions переезжают в
generated-блок, а не остаются второй копией. Ручные разделы `Text formatting`,
`Character values`, `Unicode text units`, `Double formatting profiles`,
`Number locales`, extensions и compatibility сохраняют подробные примеры и
получают ссылки на справочник. Факты, уже исчерпывающе выраженные матрицей, из
ручного текста удаляются или заменяются ссылкой.

`README.md` остаётся нормативным источником prose-контракта. Начальная оговорка
`README.ru.md` об английском оригинале сохраняется, но строки generated-матриц
обоих языков гарантированно происходят из одних semantic id.

## Генератор

`tool/generate_format_reference.dart` поддерживает два режима:

- `--write` строит оба блока и обновляет README;
- `--check` сравнивает построенные блоки с файлами, ничего не записывает и
  возвращает ненулевой exit code при расхождении.

До записи генератор обязан:

- полностью провалидировать каталог;
- найти в каждом README ровно одну пару маркеров в правильном порядке;
- построить обе локализации в памяти;
- убедиться, что semantic id и порядок строк совпадают между языками.

Ошибка на любом из этих этапов не меняет ни один файл. Запись выполняется
детерминированно с сохранением ручного prefix/suffix. Неожиданная файловая
ошибка между двумя заменами не маскируется; повторный `--write` восстанавливает
оба файла, а `--check` не позволит зафиксировать частичный результат.

Рендеринг стабилен по порядку элементов каталога, окончаниям строк и Markdown.
Генератор не запускает formatter engine для вычисления документации: expected
output является частью проверяемого контракта, а не результатом текущей
реализации, иначе ошибочная реализация сама переписала бы ожидаемое описание.

## Проверка контракта

### Внутренняя целостность каталога

Отдельные тесты отвергают:

- повторные semantic id или tokens;
- отсутствующий перевод;
- type, ссылающийся на неизвестную option/value category;
- несовпадающий порядок или состав локализованных строк;
- правило, допускающее успех и отказ, без положительного и отрицательного
  conformance-case;
- generated heading/link, которому нет соответствующего README anchor.

### Соответствие движку

`test/format_reference_contract_test.dart` выполняет случаи через
поддерживаемый API: `format`, `formatWith`, `sprintf` и `vsprintf`. Каждый
случай проверяет либо точную строку, либо runtime type ошибки; случаи с
динамическими опциями дополнительно закрепляют порядок потребления аргументов.

Для конечных множеств добавляются test-only seams:

- фактический набор `_builtInTypes` фигурного parser;
- фактический набор `_supportedTypes` printf parser;
- допустимая printf flag-mask для каждой conversion.

Validator printf использует одну внутреннюю функцию для mask и debug seam, а
не две копии switch. Seams возвращают только публично называемые коллекции и
не экспортируются из `package:format/format.dart`.

Матрица применимости brace-опций проверяется поведением на канонических
значениях каждой категории. Это надёжнее нового дублирующего production switch:
если validator меняет решение, один из положительных или отрицательных случаев
каталога меняет результат.

### Generated artifacts

`tool/verify_generated_artifacts.dart` вызывает проверку reference-блоков наряду
с Python/C++ artifacts. Она не пишет в checkout. Тесты самого генератора на
scratch-файлах покрывают отсутствующие и повторные маркеры, сохранение ручного
текста и отсутствие записи при предварительной ошибке.

Обычный обязательный прогон дополнительно сохраняет Markdown anchor tests и
автономную проверку pub-архива. Сам tool и русская документация не обязаны
попадать в pub-архив; английский README внутри архива обязан содержать уже
сгенерированный справочник.

## Рабочий процесс будущего изменения формата

1. Изменить semantic row и conformance-cases в каталоге.
2. Изменить реализацию до прохождения conformance-тестов.
3. Выполнить `dart run tool/generate_format_reference.dart --write`.
4. Просмотреть получившийся Markdown как публичный API diff.
5. Выполнить полный обязательный прогон, включая `--check` через общий verifier.

Если реализация изменилась без каталога, conformance/debug-seam tests краснеют.
Если каталог изменился без README, `--check` краснеет. Если README исправлен
вручную внутри generated-блока, `--check` краснеет. Ручные углублённые разделы
остаются предметом обычного review, но больше не повторяют полные матрицы.

## Совместимость и производительность

Публичный runtime API и результаты форматирования не меняются. Добавляются
только инструменты, тесты, документация и непубличные debug-seams. Извлечение
общей функции допустимых printf flags сохраняет ту же switch-логику; её влияние
всё равно проверяется стандартными benchmark-матрицами. Работа не заявляется
как ускорение, поэтому отдельный performance A/B и пересъёмка gate baseline не
нужны, если реализация не затронет горячий путь сверх этой механической
экстракции.

## Критерии готовности

- Оба README содержат полный generated-справочник brace и printf в описанном
  объёме.
- В README нет прежних ручных копий presentation/conversion matrices.
- Английский и русский блоки имеют один набор semantic id и один порядок.
- Каталог валиден и каждая нормативная строка имеет положительное и
  отрицательное подтверждение там, где правило допускает оба исхода.
- Публичные conformance-вызовы подтверждают результаты и классы ошибок.
- Debug-seams подтверждают полноту конечных множеств типов и printf flags.
- `generate_format_reference.dart --check` и общий generated-artifacts verifier
  ловят любое устаревание README, не меняя checkout.
- Production behavior, supported public exports и версия пакета не меняются.
- Полный обязательный список из `docs/handoff.md` проходит до implementation
  commit.
