## Цель и границы

Performance-gate должен выносить вердикт на hosted runner с любой уже
проверенной моделью процессора, не принимая число с другой модели за регрессию.
Новая запись эталона получается только из восьми отчётов, измеренных на
зафиксированной эталонной ревизии; ночной workflow сам эталоны не пополняет и
не коммитит.

Работа не меняет benchmark matrix, допуски, сценарии, production-код или
публичный API пакета. Неизвестная модель остаётся недетерминирующим исходом с
нулевым кодом выхода, как и сейчас.

## Формат и выбор эталона

`benchmark/results/gate-baseline.json` переходит на `schemaVersion: 2`.
Ниже сокращённый фрагмент существующей записи; реальный файл содержит полные
матрицы:

```json
{
  "schemaVersion": 2,
  "sourceRevision": "9143e7407e162a1fdc6b11d57515143390a04c53",
  "primaryCpu": "AMD EPYC 7763 64-Core Processor",
  "references": {
    "AMD EPYC 7763 64-Core Processor": {
      "recordedAt": "2026-08-14",
      "environment": {
        "cpu": "AMD EPYC 7763 64-Core Processor",
        "os": "linux Linux 6.17.0-1022-azure #22-Ubuntu SMP Mon Jul 27 17:24:03 UTC 2026",
        "dartVersion": "3.13.0 (stable) (Wed Aug 5 00:28:05 2026 -0700) on \"linux_x64\"",
        "nodeVersion": "v24.8.0"
      },
      "phaseMeans": { "jit/braces": { "cold": 0.4880955979458205 } },
      "scenarioRatios": { "jit/braces": { "brace.literal.cold": 0.588083202171448 } }
    }
  }
}
```

Ключ `references` обязан в точности совпадать с `environment.cpu`; список не
может быть пустым, а `primaryCpu` обязан быть его ключом. Все записи относятся
к одному корневому `sourceRevision`, но каждая сохраняет собственные Dart и
Node provenance: при точном совпадении CPU гейт выбирает эту запись и проверяет
версии с ней.

Для неизвестного CPU вычисления выполняются относительно `primaryCpu` только
как диагностические ratios. `comparable` и `decisive` при этом ложны, код выхода
остаётся нулевым, а причина однозначно говорит, что записи для измеренного CPU
нет и какая первичная запись использована только для отчёта. Это сохраняет
сегодняшнюю наблюдаемость, но не позволяет случайной первой записи в JSON стать
вердиктом.

## Запись и controlled capture

`--record=YYYY-MM-DD` создаёт новый набор с одной записью. Новый
`--add-reference=YYYY-MM-DD` читает существующий `--baseline`, требует
`--output`, валидирует восемь отчётов, требует их `sourceRevision` равным
корневому SHA и добавляет ровно запись измеренного CPU. `--output` может быть
тем же путём, что `--baseline`: файл записывается только после всех проверок.
Режим откажется от дубликата CPU, смешения режимов записи и оценки, неполного
набора либо несовместимой ревизии. Замена существующей записи намеренно не
входит в этот интерфейс: переэталонирование требует явной отдельной работы.

`workflow_dispatch` получает boolean-режим controlled capture и обязательный
в этом режиме SHA эталонной ревизии. Он checkout'ит этот SHA, строит восемь
отчётов обычным измерительным путём и выгружает их artifact'ом. Он не меняет
baseline в git и не делает оценку, если запущен для capture. Отчёты затем
добавляются локально через `--add-reference` и проходят обычное review перед
коммитом. Так незнакомая машина не может тихо записать регрессию как новый
эталон.

## Проверки и документация

TDD-тесты закрепят round-trip schema 2, выбор совпавшего CPU, diagnostic
fallback для неизвестного CPU, несовпадения Dart/Node после выбора, инварианты
формата и отказ `--add-reference` от дубликата или другой ревизии. Два CLI
прогона проверят создание первого набора и добавление второй записи без потери
первой. Проверка workflow останется статической по YAML и ручной по artifact'у:
первый реальный capture будет выполнен для текущего `sourceRevision`, после
чего в committed baseline появятся только подтверждённые CPU-ключи.

`benchmark/results/README.md` опишет структуру, ручное добавление и смысл
недетерминирующего unknown CPU. `docs/handoff.md` зафиксирует принятое решение,
коммиты, результаты capture и оставшиеся модели без записи.
