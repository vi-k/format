# Format 3.0: совместимость с Python 3.14 и `std::sprintf` C++23

## Статус и цель

Этот документ задаёт дизайн Format 3.0. Версия 3.0 заменяет внутренний движок
Format 2 единым строгим движком с двумя синтаксисами: `str.format()` Python
3.14 и `std::sprintf` C++23. Она также возвращает удобные вызовы с отдельными
позиционными значениями.

Для `{...}` нормативным контрактом служат синтаксис форматных строк и язык
спецификаций `str.format()` Python 3.14. `std::format` используется для этого
диалекта как вторичный ориентир только там, где он не противоречит Python. Для
`%...` единственным нормативным контрактом служит стандартный `std::sprintf`
C++23. Любое неизбежное отличие Dart или дополнительная возможность должно
быть явно описано и закреплено тестом.

Работа выпускается как Format 3.0 и не переписывает историю или GitHub-релиз
Format 2.0. Публикация уже подготовленного Format 2.0 на pub.dev не входит в
этот дизайн.

## Не входит в задачу

- синтаксис f-строк и выполнение произвольных выражений;
- `dart:mirrors` или иное неявное отражение структуры объектов;
- режим совместимости со старым нестрогим поведением;
- возможность заменить встроенный specifier пользовательским;
- публичный API предварительно скомпилированного шаблона;
- вычисление реальной ширины терминальных колонок;
- указательные conversions `%n` и `%p`;
- модификаторы длины `hh`, `h`, `l`, `ll`, `j`, `z`, `t`, `L`;
- POSIX-нумерация аргументов вида `%2$d`;
- необязательные conversions `%b` и `%B` из C++26;
- пользовательские conversions в `%`-синтаксисе;
- автоматическое принятие изменений будущих версий Python.

## Термины

В документе английские слова сохраняются там, где они являются частью
публичного API или общепринятого обозначения:

- specifier — обозначение типа представления в конце спецификации, например
  `f`, `X` или `json`;
- formatter — компонент, форматирующий значение;
- lookup — поиск корневого аргумента, свойства, ключа или индекса;
- conversion — предварительное преобразование `!s`, `!r` или `!a`;
- printf conversion — `%`-последовательность, преобразующая очередной аргумент;
- representation — детерминированное строковое представление для `!r`;
- format spec — спецификация после `:` внутри поля;
- fill и align — заполнитель и способ выравнивания;
- flags — однобуквенные флаги, изменяющие поведение conversion;
- width — минимальная ширина результата;
- precision — точность числа или максимальная длина строки;
- padding — дополнение результата пробелами или нулями до width;
- signed и unsigned — знаковое и беззнаковое целое представление;
- wrapping — скрытое приведение целого по модулю выбранной разрядности;
- narrow `sprintf` — стандартная C/C++-форма, работающая с `char` и байтами;
- payload — дополнительные данные пользовательского formatter;
- locale — региональные правила записи чисел;
- backend — подключаемая реализация интерфейса;
- benchmark — измерение производительности;
- JIT — компиляция во время выполнения в виртуальной машине Dart;
- AOT — предварительная компиляция в исполняемый файл;
- Unicode scalar — отдельное значение Unicode, доступное через `String.runes`;
- grapheme cluster — одна воспринимаемая пользователем составная единица
  Unicode-текста;
- stack trace — сохранённый стек вызовов исходной ошибки.

## Версионированный контракт

Эталоны фиксируются на Python 3.14 и C++23. Тестовые данные записывают точную
версию интерпретатора, компилятора и стандартной библиотеки, использованных для
их генерации. Изменения Python 3.15, C++26 и более поздних стандартов принимаются
только явно в последующих версиях пакета.

Везде, где типы и возможности платформ совпадают, результат и факт принятия
или отклонения спецификации должны совпадать с нормативным источником
соответствующего диалекта. Сообщения об ошибках не обязаны дословно совпадать:
Dart предоставляет собственную типизированную иерархию исключений вместо
неопределённого поведения C++.

## Публичный API

### Стандартный экземпляр

Пакет экспортирует неизменяемую конфигурацию стандартного движка:

```dart
final defaultFormat = Format();
```

Функции `format`, `formatWith`, `sprintf` и `vsprintf` верхнего уровня
делегируют работу этому экземпляру. В них нет отдельной логики разбора или
форматирования.

`Format` после создания не позволяет менять formatter, lookup, conversion,
locale или единицу измерения текста. Возможный внутренний кеш не считается
изменением конфигурации и не влияет на результат.

### Удобный позиционный вызов

`format` принимает шаблон и до десяти отдельных позиционных значений:

```dart
format('{} {}', 'hello', 'world');
```

`List` и `Map` всегда являются одним форматируемым значением. Они больше не
раскрываются автоматически как набор аргументов:

```dart
format('{}', [1, 2]); // форматирует один List
```

Необязательные параметры используют закрытое служебное значение, позволяющее
отличить отсутствующий аргумент от явно переданного `null`:

```dart
format('{}', null); // один аргумент со значением null
format('{}');       // MissingFormatArgumentException
```

`format` собирает только фактически переданные значения и вызывает метод
`formatWith` того же экземпляра `Format`.

### Полный вызов

`formatWith` принимает позиционные и именованные аргументы одновременно:

```dart
String formatWith(
  String template, {
  List<Object?> positional = const [],
  Map<String, Object?> named = const {},
});
```

Пример:

```dart
formatWith(
  '{0} {name}',
  positional: ['hello'],
  named: {'name': 'world'},
);
```

Отдельная функция `formatNamed` удаляется.

### Вызовы `sprintf` и `vsprintf`

`sprintf` принимает шаблон C++23 и до десяти отдельных позиционных значений:

```dart
sprintf('%d %s', 42, 'answer');
```

`vsprintf` является формой для списка любой длины и соответствует роли C
`va_list` без указателей и работы с памятью:

```dart
vsprintf(
  '%d %s',
  [42, 'answer'],
);
```

`sprintf` использует то же закрытое служебное значение для различения
отсутствующего аргумента и `null`, собирает фактически переданные значения и
вызывает `vsprintf` того же экземпляра `Format`.

Лишние значения в списке игнорируются согласно `std::sprintf`. Недостающие
значения приводят к типизированной ошибке вместо неопределённого поведения.

### Пользовательские функции

Методы экземпляра `Format` повторяют формы `format`, `formatWith`, `sprintf` и
`vsprintf`. Пользователь может создать настроенный движок и сохранить ссылки на
его методы как функции:

```dart
final applicationFormat = Format(
  formatters: [JsonFormatter()],
  lookups: [ApplicationLookup()],
);

final appFormat = applicationFormat.format;
final appFormatWith = applicationFormat.formatWith;
final appSprintf = applicationFormat.sprintf;
final appVSprintf = applicationFormat.vsprintf;
```

Все такие функции используют те же анализаторы и политики диалектов, что и
функции верхнего уровня.

## Архитектура движка

Движок имеет два независимых синтаксических анализатора и две политики
диалектов поверх общего типизированного слоя форматирования:

```text
анализатор `{...}` -> политика Python 3.14 ┐
                                          ├-> общий типизированный слой
анализатор `%...`  -> политика C++23     ┘
```

Анализатор `{...}` контролирует скобки, нумерацию, conversion и вложенность.
После него механизм разрешения полей выполняет `.attribute`, `[item]`, `!s`,
`!r` и `!a`.

Анализатор `%...` контролирует флаги, width, precision, `*`, порядок
потребления аргументов и conversion. Он не переводит шаблон во внутренний
`{...}`-шаблон.

Общий типизированный слой реализует преобразование целых чисел и `double`,
округление, знаки, padding, показатели степени, специальные значения, locale и
измерение текста. Политика диалекта определяет допустимые опции и различающуюся
семантику, например integer precision и alternate octal form.

Кеш разобранных шаблонов включает диалект в ключ, поэтому одинаковая строка не
может смешать два синтаксиса. Выбор между `RegExp`, ручным проходом и смешанным
анализатором не закрепляется дизайном: его определяют измерения первого и
повторного вызова на каждой целевой платформе.

Синтаксические анализаторы не форматируют значения, а общий слой не ищет
аргументы. Такое разделение позволяет независимо тестировать грамматику,
разрешение и числовое представление.

## Грамматика полей

Поддерживается грамматика `str.format()` Python 3.14:

```text
replacement_field = "{" [field_name] ["!" conversion] [":" format_spec] "}"
field_name        = arg_name ("." attribute_name | "[" element_index "]")*
conversion        = "s" | "r" | "a"
```

Правила:

- `{{` и `}}` выводят литеральные фигурные скобки;
- `{}` использует следующий автоматически пронумерованный позиционный аргумент;
- `{0}` использует позиционный аргумент с указанным индексом;
- `{name}` использует именованный аргумент;
- `arg_name` и `attribute_name` подчиняются правилам Unicode-идентификаторов
  Python 3.14, а числовой `arg_name` определяется как десятичное число;
- строковая часть `[item]` содержит любые символы, кроме `]`, и не допускает
  синтаксиса кавычек;
- автоматическую `{}` и ручную `{0}` нумерацию нельзя смешивать в одном
  шаблоне;
- именованные поля разрешено сочетать с автоматическими или ручными
  позиционными полями;
- старые корневые имена в кавычках удаляются;
- пробелы не отбрасываются нестрогим образом и приводят к ошибке, если нарушают
  указанную грамматику;
- форматная спецификация может содержать вложенные поля;
- вложенное поле может иметь имя, conversion и собственную спецификацию, но
  более глубокая вложенность запрещена;
- вложенные поля вычисляются до разбора итоговой спецификации;
- литеральная фигурная скобка не может непосредственно служить заполнителем,
  но может быть получена из вложенного поля согласно правилам Python.

Динамическая ширина и точность снова поддерживаются:

```dart
formatWith(
  '{value:{width}.{precision}f}',
  named: {
    'value': 12.345,
    'width': 8,
    'precision': 2,
  },
);
```

## Разрешение полей

Значение вычисляется слева направо:

```text
корневой аргумент -> .attribute / [item] -> conversion -> format spec
```

- числовой корень обращается к `positional`;
- строковый корень обращается к `named`;
- `[123]` использует целочисленный индекс;
- `[name]` использует литеральный строковый ключ без интерпретации кавычек;
- `List` поддерживает целочисленный индекс;
- `Map` поддерживает поиск элемента по ключу;
- `.name` для `Map` обращается к строковому ключу `name`;
- `.name` для прочих объектов использует явно подключённую пользовательскую
  точку расширения поиска;
- встроенный поиск `Map` и `List` имеет приоритет над пользовательскими
  расширениями;
- для пользовательского объекта должна подходить ровно одна точка расширения;
  несколько подходящих реализаций считаются неоднозначностью;
- произвольные Dart-выражения не вычисляются.

Вложенные поля используют те же наборы `positional` и `named` и подчиняются тем
же правилам нумерации и поиска.

## Преобразования `!s`, `!r` и `!a`

- `!s` вызывает `toString()` и затем форматирует полученную строку;
- `!r` создаёт детерминированное строковое представление встроенных типов;
- `!a` применяет ASCII-экранирование к результату `!r`;
- пользовательские объекты могут предоставить реализацию representation через
  отдельную точку расширения `Format`;
- несколько подходящих representation-расширений считаются неоднозначностью.

Dart не имеет прямого аналога Python `repr()`, поэтому точное представление
пользовательских объектов не имитируется неявно. Это намеренное и
документированное отличие.

Для встроенных аналогов контракт `!r` определён явно:

- `String` использует совместимые с Python кавычки и экранирование;
- `int`, `BigInt` и `double` используют совместимое числовое представление;
- `bool` и `null` используют Dart-токены `true`, `false` и `null`;
- `List`, `Map` и `Set` форматируются рекурсивно как `[...]`,
  `{key: value}` и `{...}`; пустой `Set` записывается как `set()`;
- порядок элементов контейнера равен порядку итерации Dart;
- рекурсивная ссылка контейнера обозначается многоточием и не приводит к
  бесконечному обходу;
- прочий объект без representation-расширения приводит к
  `UnsupportedConversionException`, а не к нестабильной строке с адресом.

`!a` выполняет тот же алгоритм, после чего экранирует все Unicode scalars вне
ASCII.
Точная таблица управляющих символов, выбора кавычек и рекурсивных контейнеров
закрепляется тестовыми эталонами Python и перечнем Dart-токенов выше.

## Стандартный язык спецификаций

Поддерживается общая форма Python 3.14:

```text
[[fill]align][sign][z][#][0][width][grouping]
["." (precision [grouping] | grouping)][type]
```

Где:

- `fill` — одна единица текста выбранного режима;
- `align` — `<`, `>`, `=` или `^`;
- `sign` — `+`, `-` или пробел;
- `z` нормализует отрицательный ноль после округления;
- `#` включает альтернативную форму;
- `0` включает знакоучитывающее заполнение нулями;
- `grouping` и `fractional_grouping` — `,` или `_`;
- `width` — минимальная ширина;
- `precision` имеет значение, определённое типом;
- `type` выбирает представление.

Любая опция, недопустимая для выбранного типа, приводит к
`InvalidSpecifierException`. Неизвестные символы выравнивания и заполнители из
нескольких единиц выбранного текста не принимаются.

### Строки

- `s` является явным и стандартным типом;
- пустой type равносилен `s`;
- выравнивание по умолчанию — влево;
- precision задаёт максимальное число выбранных единиц текста;
- sign, `z`, `#`, `=`, grouping и числовое zero padding запрещены;
- precision не разделяет grapheme cluster в соответствующем режиме.

### Целые числа и `BigInt`

Поддерживаются `b`, `c`, `d`, `o`, `x`, `X` и `n`.

- пустой type равносилен `d`;
- альтернативные префиксы равны `0b`, `0o`, `0x` и `0X`;
- `_` группирует двоичные, восьмеричные и шестнадцатеричные цифры по четыре;
- `,` и `_` группируют десятичные цифры по три;
- precision для целочисленных представлений запрещена;
- `c` принимает ровно один целый Unicode-код в диапазоне Python;
- `List<int>` больше не принимается для `c`;
- `c` по умолчанию выравнивается вправо как числовое представление;
- недопустимый код преобразуется в `UnsupportedFormatValueException`, а не в
  сырой `RangeError`.

Как в Python, целое число может использовать типы представления с плавающей
точкой `e`, `E`, `f`, `F`, `g`, `G` и `%` через преобразование в `double`.
Переполнение этого
преобразования становится типизированной ошибкой форматирования. Для `BigInt`
не вводится скрытое расширение диапазона, если оно изменило бы результат Python.

### `double`

Поддерживаются `e`, `E`, `f`, `F`, `g`, `G`, `n` и `%`.

- пустой type воспроизводит Python `str(float)`, а не `g` с precision 6;
- пустой type сохраняет минимум одну цифру после точки в фиксированной записи;
- `e` и `E` используют минимум две цифры показателя степени;
- `f`, `F`, `e` и `E` без precision используют шесть дробных цифр;
- `g` и `G` без precision используют шесть значащих цифр;
- precision `0` для `g` и `G` трактуется как `1`;
- выбор фиксированной или экспоненциальной записи для `g` и `G` повторяет
  пороги Python;
- округление повторяет Python round-to-nearest, ties-to-even;
- искусственное ограничение Format 2 в 18 цифр не сохраняется;
- `#` сохраняет десятичную точку, а для `g` и `G` также конечные нули;
- `z` превращает отрицательный ноль после округления в положительный;
- `%` умножает значение на 100, применяет фиксированную запись и добавляет `%`;
- `F` и `G` используют верхний регистр для `NAN` и `INF`;
- знак `+` применяется к `nan` и `inf` так же, как в Python;
- знакоучитывающее zero padding специальных значений повторяет Python, даже
  если C++ ведёт себя иначе;
- группировка дробной части повторяет правила, добавленные в Python 3.14.

### `bool`, `null` и прочие объекты

`bool` не считается числом, потому что в Dart он не является подтипом `int`.
Пустая спецификация возвращает `true` или `false`, а числовые спецификации
отклоняются.

`null` с пустой спецификацией возвращает `null`. Для прочего объекта пустая
спецификация использует единственный подходящий пользовательский formatter, а
затем `toString()`. Непустая спецификация без подходящего formatter является
ошибкой.

Представления `true`, `false` и `null` являются намеренными отличиями от Python
`True`, `False` и `None`.

## Язык `sprintf`

### Грамматика

Поддерживается подмножество стандартного `std::sprintf` C++23 без
указателей и модификаторов длины:

```text
conversion = "%" [flags] [width] ["." precision] type
flags      = любое сочетание "-", "+", space, "#", "0"
width      = decimal-digits | "*"
precision  = decimal-digits | "*" | empty
```

Поддерживаемые conversions:

```text
%%  %c  %s
%d  %i  %u  %o  %x  %X
%f  %F  %e  %E  %g  %G  %a  %A
```

Правила разбора:

- `%%` выводит `%` и не принимает flags, width или precision;
- незавершённый `%` и неизвестный conversion приводят к
  `InvalidFormatException`;
- `%n` и `%p` отклоняются, поскольку требуют указателей;
- модификаторы `hh`, `h`, `l`, `ll`, `j`, `z`, `t`, `L` отклоняются, а не
  игнорируются;
- POSIX-нумерация `%2$d` отклоняется;
- необязательные `%b` и `%B` из C++26 не входят в контракт C++23 и
  отклоняются;
- пользовательские formatter не могут добавлять `%`-conversion;
- повтор одного и того же флага не меняет результат;
- флаг, width или precision, не определённые стандартом для конкретного
  conversion, приводят к `InvalidSpecifierException`, а не игнорируются.

### Потребление и типы аргументов

Литеральные width и precision находятся в шаблоне. `*` получает значение из
следующего аргумента типа `int`. Аргументы одного conversion потребляются в
порядке:

```text
dynamic width -> dynamic precision -> formatted value
```

- отрицательная dynamic width включает флаг `-` и использует абсолютное
  значение;
- отрицательная dynamic precision считается отсутствующей;
- точка без числа задаёт precision `0`;
- лишние аргументы игнорируются согласно стандарту;
- недостающий аргумент или неверный Dart-тип приводит к типизированной ошибке
  вместо неопределённого поведения.

Допустимые Dart-типы:

- `%d` и `%i` принимают `int` и `BigInt`;
- `%u`, `%o`, `%x` и `%X` принимают только неотрицательные `int` и `BigInt`;
- conversions чисел с плавающей точкой принимают `double`;
- `%c` принимает целый допустимый Unicode scalar;
- `%s` вызывает `toString()` для любого значения, включая `null`.

Отрицательное значение для unsigned conversion отклоняется. Скрытое 32-, 53-
или 64-битное wrapping не выполняется, поскольку Dart не различает знаковые и
беззнаковые варианты типа `int`.

### Флаги, width и precision

Допустимость опций задаётся таблицей:

| Conversion | Допустимые флаги | Width | Precision |
| --- | --- | --- | --- |
| `%c` | `-` | да | нет |
| `%s` | `-` | да | да |
| `%d`, `%i` | `-`, `+`, space, `0` | да | да |
| `%u` | `-`, `0` | да | да |
| `%o`, `%x`, `%X` | `-`, `#`, `0` | да | да |
| `%f`, `%F`, `%e`, `%E`, `%g`, `%G`, `%a`, `%A` | `-`, `+`, space, `#`, `0` | да | да |
| `%%` | нет | нет | нет |

- `+` имеет приоритет над space;
- `-` имеет приоритет над `0`;
- для целых чисел явно заданная precision отключает zero padding;
- width задаёт минимальную длину и не обрезает результат;
- precision для `%s` задаёт максимальную длину;
- поля по умолчанию выравниваются вправо;
- `-` выравнивает поле влево.

### Целые conversions

- precision задаёт минимальное количество цифр;
- значение `0` с precision `0` даёт пустую строку;
- `%#o` гарантирует начальный `0`, включая нулевое значение с нулевой
  precision;
- `%#x` и `%#X` добавляют `0x` или `0X` только для ненулевого значения;
- `%d` и `%i` имеют одинаковую семантику;
- unsigned conversions не имеют скрытого wrapping.

### Conversions чисел с плавающей точкой

- `%f`/`%F`, `%e`/`%E` и `%g`/`%G` следуют правилам C++23;
- precision по умолчанию равна `6`;
- precision `0` для `%g` и `%G` трактуется как `1`;
- `%e` и `%E` выводят в экспоненте не менее двух цифр;
- `%g` и `%G` выбирают фиксированную или экспоненциальную запись по порогам
  C++23 и без флага `#` удаляют конечные нули;
- флаг `#` сохраняет десятичную точку для `%f`, `%e`, `%g` и `%a`, а для `%g`
  также сохраняет конечные нули;
- `%f` всегда использует фиксированную запись, в том числе для очень больших и
  очень малых конечных значений;
- `%a` и `%A` создают шестнадцатеричную экспоненциальную запись, например
  `0x1.8p+0`;
- `%a` и `%A` без precision выводят достаточно цифр для точного восстановления
  исходного `double`;
- округление выполняется к ближайшему чётному;
- отрицательный ноль сохраняется;
- `f`, `e`, `g` и `a` используют `inf` и `nan`, а варианты верхнего регистра —
  `INF` и `NAN`;
- zero padding специальных значений заменяется пробелами;
- там, где стандарт допускает несколько представлений, Format выбирает одно
  детерминированное представление и документирует его как выбор реализации.

Стандарт не закрепляет единственное написание всех специальных значений и
некоторых граничных результатов с плавающей точкой. Тесты различают
обязательный результат, разрешённое стандартом множество и канонический выбор
Format.

### Строки и Unicode

Стандартный narrow `sprintf` ориентирован на байты, но публичный результат Dart
является Unicode-строкой. Поэтому Format применяет выбранный `TextUnit` к `%s`,
`%c`, width и precision:

- `%s` не обрезается внутри Unicode scalar или grapheme cluster;
- `%c` создаёт один Unicode scalar вместо `unsigned char`;
- padding измеряется в тех же единицах, что и поле;
- byte-oriented truncation и создание некорректного Unicode не поддерживаются.

Это является намеренным Dart-отличием от narrow `std::sprintf`.

## Измерение текста

Публичная настройка называется `TextUnit`:

```dart
enum TextUnit {
  unicodeScalars,
  graphemeClusters,
}
```

`TextUnit.unicodeScalars` используется по умолчанию и измеряет строку через
`String.runes`. Для корректных Unicode-строк это совпадает с измерением
`str` Python 3.14.

`TextUnit.graphemeClusters` является явно включаемым расширением. Оно считает
составной символ, воспринимаемый пользователем как единое целое, одной
единицей. Например, `e` с combining accent, `👋🏽`, `🇺🇦` и семейный emoji не
разделяются.

Выбранная единица применяется ко всем связанным операциям:

- измерению ширины и выравниванию;
- строковой precision и обрезанию;
- проверке и повторению fill.

Одна настройка `TextUnit` действует на оба диалекта, включая `%s`, `%c` и
padding `sprintf`.

Grapheme cluster не равен ширине терминальной колонки. Пакет гарантирует
Unicode-сегментацию, но не пытается учитывать конкретный терминал или шрифт.

## Пользовательские formatter

Пользовательские formatter относятся только к `{...}`-диалекту. `%`-диалект
имеет закрытый стандартный набор conversions; пользовательский объект можно
передать в `%s`, который вызовет `toString()`.

Встроенные имена `b`, `c`, `d`, `e`, `E`, `f`, `F`, `g`, `G`, `n`, `o`, `s`,
`x`, `X` и `%` зарезервированы. Пользовательская регистрация с таким именем
отклоняется при создании `Format`.

Явная пользовательская спецификация имеет вид:

```text
name
name:payload
```

`name` соответствует `[A-Za-z][A-Za-z0-9_]*`. `payload` начинается после
первого следующего `:` и занимает остаток разрешённой спецификации; пустой
`payload` допустим. Фигурные скобки внутри него подчиняются общим правилам
вложенных полей.

Здесь `payload` — дополнительные данные пользовательского formatter. Например:

```dart
format('{:json}', value);
format('{:json:pretty}', value);
```

Вложенные поля внутри `payload` разрешаются до вызова formatter. Старая
дополнительная строка в кавычках удаляется.

Перед именем разрешена стандартная внешняя часть спецификации. Core применяет
только fill, alignment и width к готовому результату. Formatter получает
остальные разобранные опции и `payload` и сам обязан принять или отклонить sign,
`z`, `#`, zero, grouping и precision.

Имена пользовательских formatter уникальны в пределах `Format`. Встроенные
типы имеют приоритет при пустой спецификации. Для прочих объектов единственный
подходящий formatter используется автоматически; несколько совпадений приводят
к `AmbiguousFormatterException`.

## Конфигурация и точки расширения

`Format` принимает неизменяемые наборы:

- пользовательских formatter;
- реализаций attribute lookup;
- реализаций representation для `!r` и `!a`;
- `NumberLocale` для `n` и conversions чисел с плавающей точкой `sprintf`;
- `TextUnit`.

Глобальные `registerFormatter` и `unregisterFormatter` удаляются. Ошибки
конфигурации выявляются во время создания `Format`, до обработки шаблона.

Specifier registry отвечает только за пользовательские formatter. Lookup,
representation и locale подключаются через отдельные типизированные точки
расширения и не могут подменить встроенный specifier.

## `n`, `sprintf` и пакет `format_intl`

`n` остаётся встроенным specifier Format 3. Основной пакет владеет его
синтаксисом, преобразованием числа, округлением, precision, выбором формы записи,
знаком, заполнением и проверкой ошибок.

Основной пакет `format` больше не зависит от `intl`. Он экспортирует интерфейс
`NumberLocale` и встроенную `CNumberLocale`. Стандартный `defaultFormat`
использует `CNumberLocale`, поэтому `n` без дополнительных пакетов повторяет
начальную C locale Python. Явные `,n` и `_n` запрещены: группировка задаётся
самим locale-aware типом `n`.

Conversions чисел с плавающей точкой `sprintf` используют тот же
`NumberLocale` для десятичного разделителя, знаков, цифр и обозначения
показателя степени. При этом алгоритмы округления и выбора записи остаются в
основном пакете. Нестандартный POSIX-флаг группировки `'` не поддерживается.

Отдельный пакет располагается в `packages/format_intl`, входит в то же рабочее
пространство Pub (workspace) и зависит от `format` и `intl`. Он предоставляет
`IntlNumberLocale`, который передаёт основному пакету:

- десятичный разделитель;
- разделитель и схему группировки;
- зависящие от locale знаки;
- алфавит цифр, если locale его задаёт;
- обозначение показателя степени, когда оно нужно контракту расширения.

`IntlNumberLocale` не вызывает `NumberFormat` для основного округления или
выбора формы записи. Это предотвращает возврат расхождений Format 2 по precision
и показателю степени.

Настройка выполняется передачей зависимости в конструктор (constructor
injection):

```dart
final ukrainianFormat = Format(
  numberLocale: IntlNumberLocale('uk_UA'),
);

final formatUk = ukrainianFormat.format;
final formatWithUk = ukrainianFormat.formatWith;
final sprintfUk = ukrainianFormat.sprintf;
final vsprintfUk = ukrainianFormat.vsprintf;
```

`IntlNumberLocale.fromDefault()` снимает значение `Intl.defaultLocale` в момент
создания. Последующее изменение глобального locale не меняет уже созданный
`Format`. Динамическое слежение за `Intl.defaultLocale` не поддерживается.

Локализованный алфавит цифр и иные возможности `intl`, отсутствующие в locale
Python, документируются как расширения `format_intl`, а не как поведение
основного пакета.

## Иерархия ошибок

Все ошибки, созданные основным пакетом или locale backend, входят в иерархию
`FormattingException`:

- `InvalidFormatException` — некорректный шаблон или грамматика поля;
- `InvalidSpecifierException` — синтаксически найденная, но недопустимая
  спецификация или комбинация опций;
- `MissingFormatArgumentException` — отсутствующий позиционный или именованный
  корневой аргумент;
- `FormatLookupException` — ошибка `.attribute`, ключа или индекса;
- `UnsupportedConversionException` — неизвестный или недоступный conversion;
- `UnsupportedFormatValueException` — formatter не принимает значение;
- `FormatConfigurationException` — дубликат, зарезервированное имя или иной
  конфликт при создании `Format`;
- `AmbiguousFormatterException` — несколько пользовательских расширений
  подходят одновременно;
- `FormatExtensionException` — ошибка внутри пользовательского расширения или
  locale backend.

Исключение содержит применимые структурированные данные:

- `offset` как индекс UTF-16 code unit в исходном шаблоне;
- фрагмент поля;
- имя specifier или conversion;
- индекс, ключ или значение;
- исходную ошибку и stack trace для `FormatExtensionException`.

Для `%`-диалекта исключение дополнительно указывает полный `%`-фрагмент,
conversion и последовательный индекс аргумента. Неподдерживаемый модификатор,
отрицательное unsigned-значение, неверный тип dynamic width/precision и
недостающий аргумент различаются структурированными полями и причиной ошибки.
При ошибке `sprintf` не возвращает частичный результат.

Тесты проверяют тип и структурированные поля, но не закрепляют полный текст
человекочитаемого сообщения. Сырые `RangeError`, `FormatException` и внутренние
ошибки `intl` наружу не выходят.

## Стратегия проверки совместимости

### Тестовые эталоны Python

Скрипт с Python 3.14 создаёт сохраняемые в git наборы входных данных и
ожидаемых результатов. Это тестовые эталоны: Dart-тест читает их и сравнивает
результат Format 3 с заранее полученным результатом Python.

Эталон описывает как минимум:

- шаблон;
- типизированные позиционные и именованные значения;
- ожидаемую строку или категорию ошибки;
- версию Python;
- стабильный идентификатор сценария.

Типизированное представление должно уметь однозначно кодировать `BigInt`,
отрицательный ноль, `nan` и бесконечность, а не полагаться только на обычный
JSON number.

Python не обязан быть установлен для обычного запуска тестов. Отдельная команда
перегенерации эталонов запускается осознанно, а изменения результатов видны в
git diff.

### Намеренные расхождения

Отдельный проверяемый перечень содержит каждое утверждённое несовпадение:

- стабильный идентификатор;
- входные данные;
- результат или ошибку Python;
- ожидаемый результат или ошибку Dart;
- причину;
- ссылку на раздел пользовательской документации.

Первоначальный перечень включает как минимум:

- `true`, `false` и `null` вместо `True`, `False` и `None`;
- lookup hooks вместо Python reflection;
- `.name` для `Map` как сокращение поиска строкового ключа;
- библиотечную реализацию `!r` и `!a`;
- порядок итерации Dart для representation контейнеров;
- пользовательские specifier `name:payload`;
- явно включаемый `TextUnit.graphemeClusters`;
- locale-возможности `format_intl`, отсутствующие в Python.

Новое расхождение ломает сравнительный тест. Оно не добавляется в перечень без
отдельного проектного решения и документации.

### Тестовые эталоны `std::sprintf`

Небольшая программа C++23 вызывает настоящий `std::sprintf` и создаёт
тестовые эталоны `%`-диалекта. Она покрывает все поддерживаемые conversions,
сочетания flags, literal и dynamic width/precision, порядок аргументов,
специальные значения и граничные числа.

Сравнение значений выполняется в общей области представимых типов C++ и Dart.
Поведение `BigInt` и более широких значений Dart проверяется отдельными тестами
как документированное расширение.

Linux-эталон создаётся с `g++ -std=c++23` и glibc на `ubuntu-24.04`.
macOS-эталон создаётся с `clang++` и `libSystem`. Каждый отчёт записывает версии
компилятора, C-библиотеки, Dart и операционной системы. Эталон запускается с
`LC_ALL=C`; locale-расширения проверяются отдельными Dart-тестами.

- одинаковые результаты двух платформ становятся обязательными эталонами;
- если стандарт разрешает несколько результатов, тест хранит разрешённое
  множество;
- Format выбирает один канонический результат из разрешённого множества;
- эталон C++23 является источником корректности, а сторонний Dart-пакет
  `sprintf` не используется для определения результата.

Намеренные отличия `%`-диалекта хранятся отдельно и включают:

- отсутствие `%n`, `%p` и модификаторов длины;
- отсутствие POSIX-нумерации `$` и C++26 `%b`/`%B`;
- Unicode `TextUnit` вместо подсчёта байтов narrow `sprintf`;
- Unicode scalar для `%c` вместо `unsigned char`;
- вызов `toString()` для произвольного значения `%s` вместо требования
  указателя на строку;
- `int` и `BigInt` произвольной поддерживаемой Dart величины вместо
  фиксированной разрядности типов C;
- явную ошибку для отрицательного unsigned-значения;
- типизированную ошибку для синтаксиса, которому C++ назначает неопределённое
  поведение;
- фиксированное округление к ближайшему чётному вместо зависимости от текущего
  режима округления среды C;
- детерминированное написание специальных значений;
- locale-возможности `format_intl` сверх C locale.

### `std::format` как вторичный ориентир

Отдельные эталоны C++ покрывают общую часть `std::format`. Они записывают
компилятор и версию стандартной библиотеки. Расхождение с C++ допустимо, если
поведение совпадает с Python или явно внесено в перечень Dart-расширений.

### Разработка через тесты

Реализация следует разработке через тесты (TDD): сначала добавляется тест,
который падает по ожидаемой причине, затем минимальная реализация и только после
этого переработка внутреннего кода без изменения поведения.

Основной пакет и `format_intl` имеют отдельные модульные тесты. Интеграционные
тесты рабочего пространства подтверждают, что публичные импорты и передача
зависимости в конструктор работают без обращения к `lib/src`.

## Производительность

### Базовая версия

Format 2 на commit `86febb4` становится замороженной базовой реализацией для
сравнения. Нужный код сохраняется только внутри набора измерений
производительности и не экспортируется из пакета.

Для `%`-диалекта соперником служит замороженный исходный код Dart-пакета
`sprintf` 7.0.0, commit `f1e74f2`. Он включается только в набор измерений с
сохранением BSD-2-Clause attribution и не становится зависимостью или эталоном
корректности Format.

Сравнение Format 3 с Format 2 выполняется только для сценариев с одинаковыми
входами и результатами. Новые возможности Format 3 измеряются отдельно и не
маскируются несопоставимым отношением к Format 2.

Сравнение с `sprintf` 7.0.0 также выполняется только на пересекающихся
сценариях с одинаковыми входами и результатами. Отсутствие API-совместимости с
этим пакетом является намеренным.

### Сценарии

Набор измерений включает:

- литеральный шаблон и шаблон с интенсивным разбором;
- `format`, `formatWith` и ссылки на методы пользовательского `Format`;
- автоматические и ручные позиционные поля;
- именованные и одновременно позиционные с именованными аргументы;
- 1, 5, 10 и 50 полей;
- строки с `unicodeScalars` и `graphemeClusters`;
- `int`, `BigInt`, `double` без явного type, а также `f`, `e`, `g` и `%`;
- группировку, знак, `=`, альтернативную форму и специальные значения;
- вложенную ширину и precision;
- поиск элементов и свойств;
- `!s`, `!r` и `!a`;
- пользовательские formatter, lookup и representation;
- основной `n` и интеграцию `format_intl` на сопоставимых результатах.

Набор `sprintf` дополнительно включает:

- `sprintf`, `vsprintf` и ссылки на методы пользовательского `Format`;
- 1, 5, 10 и 50 conversions;
- literal и dynamic width/precision;
- `%s`, `%c`, signed и unsigned integers;
- `%f`, `%e`, `%g`, `%a` и варианты верхнего регистра;
- флаги, специальные значения, Unicode и locale;
- корректные шаблоны и отдельное измерение стоимости выявления ошибок.

Каждый сценарий сначала проверяет результат и только затем измеряет время.

### Первый и повторный вызов

Результаты разделяются на:

- первый вызов с ранее не встречавшимся шаблоном, включающий стоимость разбора;
- повторные вызовы одного шаблона, отражающие обычную длительную нагрузку.

Для первого вызова заранее создаётся набор уникальных шаблонов. Время создания
этих строк не входит в измерение, а каждый шаблон используется один раз. Это
исключает попадание в кеш и измеряет разбор вместе с форматированием.

Ограниченный внутренний кеш разобранных шаблонов разрешён только при
подтверждённой измерениями необходимости. Лимит должен исключать неограниченный
рост памяти. Стоимость первого разбора публикуется отдельно, чтобы кеш её не
скрывал. Публичный API предварительно разобранного шаблона в Format 3.0 не
добавляется.

### Методика и пороги

Измерения `{...}` выполняются в JIT и AOT. Измерения `%...` выполняются в трёх
режимах:

- JIT — в виртуальной машине Dart с компиляцией во время выполнения;
- AOT — в заранее скомпилированном исполняемом файле.
- JavaScript — после `dart compile js` в закреплённой версии Node.js.

После прогрева выполняется не менее семи чередующихся измерений сравниваемых
движков. Основной показатель сценария — медиана. Весь набор запускается дважды
для подтверждения воспроизводимости.

Приёмочные пороги `{...}` относительно Format 2:

- среднее геометрическое отношений времени сопоставимых повторных сценариев не
  превышает `1.02`, то есть замедление набора не больше 2%;
- ни один ключевой сценарий не имеет воспроизводимого отношения выше `1.05`,
  то есть замедления больше 5%;
- превышение порога считается воспроизводимым только после двух независимых
  запусков в соответствующем режиме;
- пороги проверяются отдельно для JIT и AOT;
- размер AOT-файла записывается в отчёт как информационный показатель, но
  не является блокирующим критерием Format 3.0.

Приёмочные пороги `%...` относительно `sprintf` 7.0.0:

- среднее геометрическое отношений времени первого вызова не превышает `0.90`,
  то есть Format минимум на 10% быстрее;
- среднее геометрическое отношений времени повторного вызова не превышает
  `0.80`, то есть Format минимум на 20% быстрее;
- ни один ключевой сценарий не имеет воспроизводимого отношения выше `1.02`,
  то есть не отстаёт более чем на 2%;
- пороги проверяются отдельно для JIT, AOT и JavaScript;
- кеш не участвует в измерении первого вызова.

Перед реализацией `%`-анализатора отдельное измерение сравнивает заранее
созданный `RegExp`, ручной проход и смешанный вариант. Дизайн не исключает
регулярные выражения: выбирается вариант, прошедший фактические измерения на
целевых платформах.

Измерение выводит абсолютное время, отношение Format 3 к соответствующей
базовой реализации и итоговый статус каждого порога. Успешные обычные тесты не
заменяют прохождение этого проверочного этапа.

Linux-проверка является обязательной задачей GitHub Actions на
`ubuntu-24.04`. Она собирает эталон C++23, запускает Dart-тесты и выполняет
JIT-, AOT- и JavaScript-измерения. Версии `g++`, glibc, Dart и Node.js
записываются в JSON-отчёт, который сохраняется как артефакт сборки.

Аналогичная macOS-задача использует `clang++` и `libSystem`. Format 3 нельзя
считать завершённым до успешного прохождения обязательных Linux- и
macOS-проверок.

## Структура пакетов

Репозиторий становится рабочим пространством Pub с двумя пакетами:

```text
format/                 основной пакет Format 3.0
packages/format_intl/   необязательный адаптер locale
```

Корневой `format` сохраняет зависимость `characters` для явно включаемого
разделения на grapheme clusters и удаляет зависимость `intl`. `format_intl`
имеет собственные
`pubspec.yaml`, README, changelog, анализ и тесты. Его версия развивается
независимо, а зависимость от основного пакета начинается с `format ^3.0.0`.

## Документация и переход

README сохраняет текущий язык проекта и получает:

- явное утверждение о нормативном контракте Python 3.14;
- явное утверждение о нормативном контракте `std::sprintf` C++23 и вторичной
  роли `std::format`;
- краткое описание намеренных расхождений;
- четыре функции верхнего уровня и пользовательские экземпляры `Format`;
- полный поддерживаемый язык спецификаций;
- поиск, conversion и вложенные поля;
- пользовательские formatter и их `payload`;
- `TextUnit` и различие Unicode scalar/grapheme cluster;
- базовый `n` и подключение `format_intl`;
- `sprintf`/`vsprintf`, таблицу поддерживаемых conversions и неподдерживаемых
  указательных или платформенных возможностей;
- Unicode- и locale-семантику `%`-диалекта;
- отличие от byte-oriented API C++ и отсутствие совместимости с API Dart-пакета
  `sprintf` 7.0.0;
- воспроизводимые команды JIT-, AOT- и JavaScript-измерений;
- ссылку на результаты измерения производительности;
- отдельные разделы перехода с Format 1.6 и Format 2.0.

### Переход с Format 1.6

Раздел содержит таблицу «Format 1.6 -> Format 3.0» и объясняет:

- сохранённый удобный вызов `format(template, value1, value2, ...)`;
- предел в десять удобных позиционных значений и `formatWith` для списка любой
  длины;
- удаление автоматического раскрытия `List` и `Map`;
- передачу именованных аргументов через `formatWith(named: ...)`;
- одновременную передачу позиционных и именованных аргументов;
- удаление String extensions, `print` и `Map<Symbol, Object?>`;
- запрет смешивания автоматической и ручной нумерации;
- совместимые с Python динамические width и precision;
- изменения `f`, `e`, `g`, `#b`, `#o`, `#X`, `%`, `=`, `n`, `c`, `nan` и
  `inf`;
- типизированные ошибки;
- перенос locale-aware `n` в `format_intl`.

Примеры отдельно различают передачу списка как одного значения и раскрытие
списка как позиционных аргументов:

```dart
format('{}', values); // один List
formatWith('{} {}', positional: values); // несколько аргументов
```

### Переход с Format 2.0

Раздел содержит таблицу «Format 2.0 -> Format 3.0» и объясняет:

- `format(template, values)` -> `formatWith(template, positional: values)`;
- `formatNamed(template, values)` -> `formatWith(template, named: values)`;
- возвращение удобных отдельных позиционных аргументов;
- удаление глобального изменяемого реестра в пользу
  `Format(formatters: ...)`;
- новую модель lookup, representation и пользовательского `payload`;
- возвращение dynamic width и precision;
- строгую Python-грамматику и запрет смешанной нумерации;
- изменения всех граничных числовых случаев;
- `CNumberLocale` по умолчанию и отдельный `format_intl`;
- `TextUnit.unicodeScalars` по умолчанию и явно включаемый режим
  `graphemeClusters`;
- новую иерархию ошибок.

README даёт самостоятельный маршрут для каждой исходной версии: пользователю
Format 1.6 не требуется сначала изучать изменения Format 2.0.

## Критерии готовности дизайна

Format 3.0 считается реализованным только когда одновременно выполнено
следующее:

- публичные `format`, `formatWith`, `sprintf`, `vsprintf` и методы `Format`
  соответствуют этому документу;
- тестовые эталоны Python 3.14 проходят;
- тестовые эталоны `std::sprintf` C++23 проходят на Linux и macOS;
- каждое несовпадение находится в утверждённом перечне намеренных расхождений;
- `std::format`-сравнение не выявляет необъяснённых отличий в общей области;
- основной пакет не зависит от `intl`;
- `format_intl` проходит собственные и интеграционные тесты рабочего
  пространства;
- анализаторы, форматирование исходников и весь набор тестов проходят;
- `{...}` проходит JIT- и AOT-пороги относительно Format 2;
- `%...` проходит пороги первого и повторного вызова относительно `sprintf`
  7.0.0 в JIT, AOT и JavaScript;
- обязательные Linux- и macOS-задачи GitHub Actions проходят и сохраняют
  отчёты;
- README содержит переходы как с Format 1.6, так и с Format 2.0;
- перед заявлением о завершении выполнена отдельная итоговая проверка
  (`verification-before-completion`).
