# Оптимизация форматирования больших десятичных целых чисел

## Цель

Устранить подтверждённую регрессию Format 3 относительно Format 2 при
форматировании больших десятичных `int`, не меняя результат форматирования,
публичный API и правила обработки `BigInt`.

## Исходные данные

В пользовательском benchmark Format 3 отстаёт на больших `int` примерно в
2,7–3,8 раза. Изолированное измерение показало:

- `int.toString()` — около 0,138 мкс;
- `BigInt.from(int).toString()` — около 0,372 мкс;
- `BigInt.from(int).toRadixString(10)` — около 2,604 мкс;
- полный Format 3 для `{:d}` — около 3,100 мкс.

Текущий `formatBraceInteger` всегда преобразует `int` в `BigInt`, после чего
`formatMagnitude` вызывает `toRadixString(10)`. Format 2 использует прямой
десятичный `toString()` для обычного `int`.

## Рассмотренные подходы

### 1. Десятичный fast path в `formatMagnitude` — первый шаг

При radix 10 вызывать `BigInt.toString()`, для radix 2/8/16 сохранить
`toRadixString(radix)`. Это минимальное изменение, которое устраняет самый
дорогой подтверждённый участок и одновременно ускоряет brace/printf decimal.

Плюсы: малый риск, одна точка изменения, неизменная семантика. Минус: для
обычного `int` остаётся промежуточный `BigInt.from`.

### 2. Отдельный путь для `int` — условный второй шаг

Если первого шага недостаточно для performance gate, не преобразовывать
обычный `int` в `BigInt`: определять знак на исходном значении, получать строку
через `int.toString()`/`toRadixString()` и удалять ведущий минус перед layout.
`BigInt` продолжает использовать собственный путь.

Плюсы: максимальная производительность. Минус: больше ветвлений и отдельная
проверка минимального отрицательного `int`.

### 3. Оптимизация парсера или кэш шаблонов — отклонено

Парсер добавляет значительно меньшую постоянную стоимость и не объясняет
зависимость замедления от величины числа. Этот подход не устраняет найденную
причину.

## Выбранный дизайн

1. Добавить в корневую benchmark-матрицу ключевой hot-сценарий
   `brace.int.large_decimal.hot` с `9007199254740991`, шаблоном `{:d}` и
   frozen Format 2 в качестве baseline. Это максимальный точно представимый
   JavaScript `int`, поэтому сценарий не ломает общий dart2js harness; реальные
   64-битные границы отдельно остаются в VM correctness-тестах.
2. Зафиксировать RED фактическим ratio этого сценария. Timing-порог не
   добавлять в обычные unit-тесты: сценарий использует существующий
   воспроизводимый benchmark gate с медианами и повторными запусками.
3. В `formatMagnitude` использовать `magnitude.toString()` при radix 10.
4. Повторить измерение. Если ключевой сценарий не укладывается в существующий
   порог 1,05, реализовать отдельный `int` fast path из подхода 2.
5. Не менять parser, публичный API и пользовательские незакоммиченные файлы в
   `example/` и `.vscode/`.

## Корректность и крайние случаи

Проверки должны сохранить результаты для:

- `0`, положительных и отрицательных `int`;
- `9223372036854775807` и `-9223372036854775808`;
- положительных и отрицательных `BigInt` за пределами `int`;
- `d` и `n`, знака, ширины, zero padding и группировки;
- недесятичных `b`, `o`, `x`, `X` без изменения их пути.

## Проверка результата

- focused unit-тесты integer/printf и benchmark matrix;
- полный `dart test` и `dart analyze`;
- пользовательский `example/bin/benchmark.dart` до и после;
- ключевой large-decimal сценарий в JIT и AOT;
- JS correctness/smoke в поддерживаемой существующим harness конфигурации;
- отсутствие изменений production API и пользовательских незакоммиченных
  файлов.

Критерий успеха: поведение полностью сохраняется, а
`brace.int.large_decimal.hot` проходит существующий key gate либо, если
окружение не позволяет получить gateable run, показывает устойчивое улучшение
в двух последовательных измерениях с зафиксированной provenance.
